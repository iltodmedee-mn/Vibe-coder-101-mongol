# UI prototype

Нэг route дээр **эрс өөр хэд хэдэн UI хувилбар** үүсгэ, доод талын хөвөгч мөрөөр хооронд нь сэлгэнэ. Хэрэглэгч browser дээрээ хувилбаруудыг гүйлгэж үзээд нэгийг нь сонгоно (эсвэл тус бүрээс нь хэсэг авна), үлдсэнийг нь хаяна.

Асуулт нь харагдах байдлын биш, логик/state-ийн тухай бол энэ буруу салаа. [LOGIC.md](LOGIC.md)-г ашигла.

## Энэ хэлбэр хэзээ зөв вэ

- "Энэ хуудас ямар харагдах ёстой вэ?"
- "Энэ dashboard-ыг шийдэхээсээ өмнө хэдэн хувилбар хармаар байна."
- "Тохиргооны дэлгэцэд өөр layout туршаад үз."
- Хэрэглэгч толгой дотроо гурван бүрхэг mockup-аас сонгох гэж бүтэн өдөр зарцуулах байсан аливаа үед.

## Хоёр дэд хэлбэр: A дэд хэлбэрийг илүүд үз

UI prototype нь **аппын бусад хэсэгтэй зэрэгцэж** байхдаа дүгнэхэд хамаагүй амар: бодит header, бодит sidebar, бодит өгөгдөл, бодит нягтрал. Ганцаараа байгаа хаях route бол хоосон орон зай: тусгаарлагдсан үед хувилбар бүр зүгээр харагдана. Хувилбаруудыг байрлуулах боломжтой одоо байгаа хуудас байвал үргэлж A дэд хэлбэрийг сонго. Prototype-д ойрхон гэр үнэхээр байхгүй үед л B дэд хэлбэр рүү ор.

### A дэд хэлбэр: одоо байгаа хуудсыг өөрчлөх (илүүд үзнэ)

Route аль хэдийн байгаа. Хувилбарууд **ижил route дээр** `?variant=` URL search param-аар ялгагдан зурагдана. Одоо байгаа data fetching, param, auth бүгд хэвээр. Зөвхөн зурах хэсэг солигдоно. Энэ бол анхдагч; тодорхой шалтгаан байхгүй бол үүнийг сонго.

Prototype хийж буй зүйл одоохондоо хуудасгүй ч _угаасаа нэг хуудсан дотор байх_ зүйл бол (dashboard-ын шинэ хэсэг, тохиргооны дэлгэц дээрх шинэ card, одоо байгаа урсгалын шинэ алхам) энэ нь мөн A дэд хэлбэр. Хувилбаруудыг тэр хуудсан дотор байрлуул.

### B дэд хэлбэр: шинэ хуудас (хамгийн сүүлийн арга)

Prototype хийж буй зүйлд байрлах одоо байгаа хуудас үнэхээр байхгүй үед л ашигла (жишээ нь цоо шинэ дээд түвшний хэсэг, эсвэл хаана ч утга учиртай суулгаж болохгүй урсгал).

Төслийн одоо байгаа routing-ийн дүрмийг дагаж **хаях route** үүсгэ. Шинэ дээд түвшний бүтэц бүү зохио. Prototype гэдэг нь илт харагдахаар нэрлэ (жишээ нь зам эсвэл файлын нэрэнд `prototype` гэдэг үг оруул). Мөн адил `?variant=` загвар.

B дэд хэлбэрийг сонгохоосоо өмнө шалга: үүнийг суулгаж болох одоо байгаа хуудас үнэхээр байхгүй юу? Хоосон route нь өгөгдөлтэй route-ийн ил гаргах дизайны асуудлыг нууна.

Хоёр дэд хэлбэрт доод талын хөвөгч мөр адилхан.

## Явц

### 1. Асуултаа хэлж, N-ээ сонго

Анхдагчаар **3 хувилбар**. 5-аас олон болохоор эрс өөр байхаа больж шуугиан болдог, тиймээс 5-аар хязгаарла.

Төлөвлөгөөгөө нэг мөрөөр prototype-ийн байрлалд эсвэл файлын дээд талын comment-д бич:

> "Тохиргооны хуудасны гурван хувилбар, `?variant=`-аар сэлгэнэ, одоо байгаа `/settings` route дээр."

Хэрэглэгч хажууд байж эсэргүүцэх эсэхээс үл хамааран ажиллана.

### 2. Эрс өөр хувилбарууд үүсгэ

Хувилбар бүрийн ноорогийг гарга. Тус бүрийг дараахад нийцүүл:

- Хуудасны зорилго болон түүний хандаж чадах өгөгдөл.
- Төслийн component library / styling систем (TailwindCSS, shadcn, MUI, энгийн CSS, юу ч байсан).
- Тодорхой export хийсэн component-ийн нэр, жишээ нь `VariantA`, `VariantB`, `VariantC`.

Хувилбарууд **бүтцээрээ өөр** байх ёстой: өөр layout, өөр мэдээллийн шатлал, өөр гол үйлдэл, зөвхөн өнгө өөр биш. Бага зэрэг засварласан гурван card grid бол UI prototype биш, ханын цаас. Хоёр ноорог хэт адилхан гарвал нэгийг нь "card grid бүү ашигла" гэсэн тодорхой зааварчилгаатайгаар дахин хий.

### 3. Тэднийг холбо

Route дээр ганц сэлгэгч component үүсгэ:

```tsx
// pseudo-code, төслийн framework-т тохируул
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

A дэд хэлбэрт (одоо байгаа хуудас): одоо байгаа data fetching-ийг бүгдийг сэлгэгчээс дээш үлдээ; хувилбар бүрт зөвхөн зурагдах дэд мод солигдоно.

B дэд хэлбэрт (шинэ хуудас): `/prototype/<name>` доорх хаях route ижил сэлгэгчийг байрлуулна.

### 4. Хөвөгч сэлгэгчээ бүтээ

Дэлгэцийн доод голд тогтсон байрлалтай жижиг мөр, гурван хэсэгтэй:

- **Зүүн сум**: өмнөх хувилбар руу шилжинэ (эргэлдэнэ).
- **Хувилбарын шошго**: одоогийн хувилбарын түлхүүр, хэрэв хувилбар нэр export хийдэг бол тэр нэрийг ч харуулна. Жишээ нь `B (Sidebar layout)`.
- **Баруун сум**: дараагийнх руу шилжинэ (эргэлдэнэ).

Зан төлөв:

- Сум дарахад URL search param шинэчлэгдэнэ (framework-ийн router-ийг ашигла, жишээ нь Next дээр `router.replace`, React Router дээр `navigate` гэх мэт), тэгвэл хувилбарыг хуваалцаж болно, reload хийхэд хэвээр үлдэнэ.
- Гар: `←` ба `→` сумнууд мөн сэлгэнэ. `<input>`, `<textarea>`, эсвэл `[contenteditable]` дээр focus байхад сумны товчийг бүү барь.
- Хуудаснаас илт ялгаатай харагдана (жишээ нь өндөр contrast-тай pill хэлбэр, бүдэг сүүдэр), тэгвэл үнэлж буй дизайны нэг хэсэг биш гэдэг нь ойлгомжтой.
- Production build-д нуугдана: `process.env.NODE_ENV !== 'production'` эсвэл түүнтэй адил шалгалтаар хаалт хий, тэгвэл санамсаргүй merge болсон prototype мөрийг хэрэглэгчид рүү гаргахгүй.

Хоёр дэд хэлбэр дахин ашиглаж болохоор сэлгэгчийг ганц хуваалцсан component-д хий. Төсөлд хуваалцсан UI хаана байдаг, тэнд байрлуул.

### 5. Хүлээлгэж өг

URL-аа (болон `?variant=` түлхүүрүүдийг) харуул. Хэрэглэгч боломж гарахаараа гүйлгэж үзнэ. Хамгийн сонирхолтой санал ихэвчлэн **"B-ийн header, C-ийн sidebar-тай хүсэж байна"** гэх мэт байдаг бөгөөд энэ бол тэдний үнэхээр хүсч буй дизайн.

### 6. Хариултаа хадгалж, цэвэрлэ

Нэг хувилбар ялмагц хариултаа хадгал (аль хувилбар, яагаад), дараа нь prototype-ийг [SKILL](SKILL.md)-д бичсэнээр хадгал. Ялагчийг бодит код руу оруулж, үлдсэнийг main руу биш, хаях branch руу зөө:

- **A дэд хэлбэр**: ялагчийг одоо байгаа хуудас руу оруул; ялагдсан хувилбарууд болон сэлгэгчийг main-аас хас.
- **B дэд хэлбэр**: ялсан хувилбарыг жинхэнэ route болго; хаях route болон сэлгэгчийг main-аас хас.

Бүх хувилбарын иж бүрдэл бол анхдагч эх сурвалж, тиймээс хогийн сав руу биш, хаях branch руу очно. Учир нь main branch-д үлдсэн хувилбарын component-ууд болон сэлгэгч хурдан муудаж, дараагийн уншигчийг төөрөгдүүлнэ.

## Анти-паттернууд

- **Зөвхөн өнгө эсвэл текстээрээ ялгаатай хувилбарууд.** Энэ бол засвар, prototype биш. Жинхэнэ хувилбарууд бүтцээрээ санал зөрнө.
- **Хувилбаруудын хооронд хэт их код хуваалцах.** Хуваалцсан `<Header>` бол зүгээр; хуваалцсан `<Layout>` бол зорилгоо алдана. Хувилбар бүр layout-аа хаях эрх чөлөөтэй байх ёстой.
- **Хувилбаруудыг бодит өөрчлөлт (mutation) рүү холбох.** Зөвхөн уншдаг prototype зүгээр. Хувилбар өөрчлөлт хийх шаардлагатай бол stub руу чиглүүл: асуулт нь "энэ ямар харагдах ёстой вэ", "backend ажиллаж байна уу" биш.
- **Prototype-ийг шууд production болгох.** Хувилбарын код prototype-ийн хязгаарлалтаар бичигдсэн (test байхгүй, алдааны боловсруулалт хамгийн бага). Бодит код руу оруулахдаа зөв дахин бич.
