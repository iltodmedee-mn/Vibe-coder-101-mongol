# Логикийн prototype

Хэн ч товч дарж state model-ийг удирдаж болох, бүх зүйлээ агуулсан ганц HTML файл (**хуваалцаж болох demo**). Асуулт нь **бизнесийн логик, state-ийн шилжилт, эсвэл өгөгдлийн хэлбэрийн** тухай үед ашигла: цаасан дээр зүгээр харагддаг ч бодит тохиолдлуудаар давуулж үзэхээр л буруу санагддаг зүйлс.

Ганц файл, суулгах юмгүй тул код мэдэхгүй хүнд (дизайнер, PM, тухайн салбарын мэргэжилтэн) өгч, model-ийг өөрөө мэдрүүлж болно. Тиймээс энэ нь кодын биш, тэдний хэлээр ярина.

## Энэ хэлбэр хэзээ зөв вэ

- "Энэ state machine X дараа нь Y болох edge case-ийг зөв шийдэж байгаа эсэхэд итгэлгүй байна."
- "Энэ өгөгдлийн model ... гэсэн тохиолдлыг үнэхээр илэрхийлж чадах уу?"
- "API ямар байх ёстойг бичихээсээ өмнө мэдэрч үзмээр байна."
- Хэн нэгэн **товч дараад state өөрчлөгдөхийг харахыг** хүссэн аливаа зүйл.

Асуулт нь "энэ ямар харагдах ёстой вэ" бол энэ буруу салаа. [UI.md](UI.md)-г ашигла.

## Явц

### 1. Асуултаа хэл

Код бичихээсээ өмнө ямар state model, ямар асуултын prototype хийж байгаагаа бич. Нэг догол мөр, demo-гийн дээд хэсэгт (зөвхөн comment биш, харагдах танилцуулга хэсэгт). Буруу асуултад хариулсан логикийн prototype цэвэр дэмий, тиймээс хэрэглэгч одоо харж байгаа ч, дараа нь хажууд байхгүй үедээ эргэж ирсэн ч шалгаж болохоор асуултаа тодорхой бич.

### 2. Логикийг зөөвөрлөж болох module-д тусгаарла

Бодит логикийг (асуултад хариулж буй хэсгийг) ганц `<script>` блокт, дараа нь бодит codebase руу сугалж аваад тавьж болох жижиг, цэвэр (pure) module хэлбэрээр бич. Эргэн тойрны хуудас хаягдана; энэ module хаягдахгүй.

Зөв хэлбэр нь асуултаас хамаарна:

- **Цэвэр reducer**: `(state, action) => state`. Үйлдлүүд нь салангид үйл явдал, state нь ганц утга бол тохиромжтой.
- **State machine**: тодорхой state-үүд ба шилжилтүүд. "Яг одоо аль үйлдэл зөвшөөрөгдөх вэ" гэдэг нь асуултын нэг хэсэг бол тохиромжтой.
- Энгийн өгөгдлийн төрөл дээр ажилладаг **цөөн цэвэр функц**. Далд одоогийн state байхгүй, зөвхөн хувиргалт байвал тохиромжтой.
- Логик нь үнэхээр тасралтгүй дотоод state-ийг эзэмшдэг бол **тодорхой method-уудтай class эсвэл module**.

Хуудастай холбоход аль нь хамгийн амархан биш, асуултад аль нь хамгийн сайн тохирохыг сонго. Цэвэр байлга: DOM, `document`, дотор нь гар хийх товчны handler байхгүй. Хуудас түүнийг дууддаг; эсрэг чиглэлд юу ч урсахгүй. Энэ нь prototype-ийг өөрийн насаас цааш хэрэгтэй болгодог: асуултад хариулсны дараа батлагдсан reducer / machine / функцүүд бодит module руу бие даан шилжинэ.

### 3. Хуваалцаж болох HTML файлаа бүтээ

Ганц файл, энгийн HTML/CSS/JS: framework, bundler, server байхгүй, бүх зүйл дотроо байгаа тул хоёр дарахад нээгдэж, email-ээр дамжсан ч эвдрэхгүй. Хэн ч нээгээд л ажиллуулж чаддаг байх ёстой.

Код мэдэхгүй хүнд зориулж бич. Шошго бүр кодын биш, **domain-ийн хэлээр**: товч ба state нь reducer шиг биш, бизнес шиг уншигдана. Юу болж байгааг энгийн үгээр тайлбарла.

Дээрээс доош тодорхой шатлалтай байрлуул:

1. **Гарчиг ба нэг мөр тайлбар**: энэ demo юуг судлах боломж өгч байгаа (1-р алхмын асуулт).
2. **Одоогийн state**: холбогдох state бүтнээрээ, уншихад хялбар самбар хэлбэрээр (түүхий JSON биш, шошготой талбарууд), товч дарах бүрт дахин зурагдаж, өөрчлөлт харагдана. Код мэдэхгүй хүнд ойлгоход тус болох бол юу дөнгөж өөрчлөгдсөнийг онцол.
3. **Чөлөөт товчнууд**: үйлдэл бүрт нэг товч, үргэлж бэлэн, тэгвэл хэн ч model-ийг дурын дарааллаар оролдож үзнэ. Дарах бүрт үйлдлээ илгээгээд state-ийг дахин зурна.
4. **Хөтөлсөн walkthrough-ууд**: tab бүрт нэг **сценари**. Tab бүрт сценарийн товч, энгийн тайлбар (ямар нөхцөл үүсгэж, юуг ажиглах вэ), доор нь тэр сценарид **дарах товчнууд** дарааллаараа байна. Алхам бүр бодит товч: дарахад тэр үйлдлийг хийгээд дараагийн алхам руу шилжинэ. Walkthrough эхлэхэд мэдэгдэж буй анхны state руу reset хийнэ, тэгвэл сценари үргэлж ижил явна.

Хэцүү, цаасан дээр бодоход бэрх тохиолдлуудыг харуулах сценари сонго: аз жаргалтай зам (happy path), төвөгтэй edge case, хориотой байх ёстой зүйлийг оролдох.

Гоё боловч даруу байлга: цэвэр үсэг, өргөн зай, нэг онцлох өнгө. Animation, гоёл байхгүй: state ба товчнуудтай өрсөлдөх юу ч байхгүй.

### 4. Хүлээлгэж өг

Файлыг илгээ, эсвэл тэдэнд нээж өг. Тэд боломж гарахаараа walkthrough болон чөлөөт товчнуудаар дарж үзнэ. Сонирхолтой мөч бол тэд "хүлээгээрэй, ийм зүйл боломжгүй байх ёстой" эсвэл "хм, X өөр байна гэж бодсон" гэх үе. Эдгээр бол _санааны_ bug, яг үүний төлөө л хийсэн. Шинэ үйлдэл эсвэл шинэ сценари хүсвэл нэм. Prototype хөгжиж өөрчлөгддөг.

### 5. Хариулт болон prototype-оо хадгал

Prototype асуултдаа хариулмагц хариултаа хадгал, дараа нь prototype-ийг [SKILL](SKILL.md)-д бичсэнээр хадгал. Логикт хамаарах хуваарилалт: батлагдсан reducer / machine / функцүүд бодит module руу шилжинэ (шийдвэр шингэсэн); HTML бүрхүүл нь prototype-ийг анхдагч эх сурвалж болгон хадгалдаг хаях branch руу хамт очно. Бүх зүйлээ агуулсан ганц файл тул тэнд ч амархан дахин ажиллана.

## Анти-паттернууд

- **Test бүү нэм.** Test шаарддаг prototype prototype байхаа больсон.
- **Бодит database-тэй бүү холбо.** Асуулт яг persistence-ийн тухай биш л бол санах ойн state ашигла.
- **Бүү ерөнхийл.** "Дараа нь X-ийг дэмжих бол яах вэ" гэж байхгүй. Prototype нэг асуултад хариулна.
- **Логик ба хуудсыг бүү холь.** Цэвэр module нь DOM, `document`, эсвэл товчны handler-ийг дурдвал сугалж авах боломжгүй болно. Хуудсыг цэвэр module дээрх нимгэн бүрхүүл байлга.
- **Framework, bundler, server бүү ашигла.** Хүлээн авагч хоёр дарж нээдэг ганц файл; React апп эсвэл dev server "хуваалцаж болох" гэдгийг үгүй хийнэ.
- **HTML бүрхүүлийг production руу бүү гарга.** Хуудас нь гараар дарж үзэхэд зориулагдсан. Цаана нь байгаа логикийн module л хадгалах үнэ цэнтэй.
