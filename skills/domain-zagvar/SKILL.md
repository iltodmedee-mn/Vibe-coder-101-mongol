# Domain загвар

Дизайн хийх явцдаа төслийн domain загварыг (апп-ын бизнесийн ойлголтууд, тэдгээрийн нэр, хоорондын холбоо) идэвхтэй бүтээж, хурцал. Энэ бол *идэвхтэй* дадал: нэр томъёог эргэлзэн шалгах, онцгой тохиолдлын (edge case) хувилбар зохиох, нэр томъёо ба шийдвэрүүд тодорхой болмогц шууд бичиж үлдээх. (`GLOSSARY.md`-г зөвхөн үг хэллэгийн төлөө *унших* нь энэ skill биш: энэ бол аль ч skill хийж чадах нэг мөрийн зуршил. Энэ skill нь загварыг зүгээр ашиглах биш, өөрчлөх үед зориулагдсан.)

## Файлын бүтэц

Ихэнх repo нэг context-тэй:

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

Root-д `GLOSSARY-MAP.md` байвал repo олон context-тэй. Map нь context бүр хаана байгааг заана:

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← бүх системд хамаарах шийдвэрүүд
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← тухайн context-ийн шийдвэрүүд
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

Файлыг хэрэгтэй болсон үед нь л үүсгэ: бичих зүйл гарсан үед. `GLOSSARY.md` байхгүй бол эхний нэр томъёо шийдэгдэхэд үүсгэ. `docs/adr/` байхгүй бол эхний ADR хэрэгтэй болоход үүсгэ.

## Ярилцлагын үеэр

### GLOSSARY.md-тэй тулгаж шалга

Хэрэглэгч `GLOSSARY.md`-д байгаа нэр томъёотой зөрчилдөх үг хэрэглэвэл тэр дор нь хэл. "Чиний GLOSSARY.md-д 'цуцлалт'-ыг X гэж тодорхойлсон, гэтэл чи Y гэж хэлж байх шиг байна. Аль нь вэ?"

### Бүрхэг үгийг тодруул

Хэрэглэгч бүрхэг, эсвэл олон утгатай үг хэрэглэвэл нэг тодорхой, үндсэн нэр санал болго. "Чи 'аккаунт' гэж байна: Үйлчлүүлэгчийг хэлж байна уу, Хэрэглэгчийг үү? Энэ хоёр өөр зүйл."

### Бодит хувилбараар ярилц

Domain-ийн ойлголтуудын хоорондын холбоог ярилцаж байх үед тодорхой хувилбараар шалга. Онцгой тохиолдлыг сорих хувилбар зохиож, ойлголтуудын хоорондын хил хязгаарыг хэрэглэгчээр тодорхой хэлүүл. Жишээ нь: "Нэг үйлчлүүлэгч хэд хэдэн нэвтрэх эрхтэй байж болох уу?", "Захиалгын ганц барааг цуцалбал нэхэмжлэх юу болох вэ?" Зохиосон хувилбар бол асуулт, бизнесийн дүрэм биш: хэрэглэгч хариулахаас өмнө дүрэм болгож бүү бич.

### Кодтой тулгаж шалга

Хэрэглэгч ямар нэг зүйл хэрхэн ажилладгийг хэлэхэд код үүнтэй тохирч байгаа эсэхийг шалга. Зөрчил олбол ил гарга: "Чиний код Захиалгыг бүхэлд нь цуцалдаг, гэтэл чи сая хэсэгчлэн цуцалж болно гэлээ. Аль нь зөв бэ?" Код нь одоо юу хийж байгааг харуулдаг, хэрэглэгч юу хүсэж байгааг биш: аль нь зөвийг өөрөө бүү шийд.

### GLOSSARY.md-г тэр дор нь шинэчил

Нэр томъёо шийдэгдмэгц `GLOSSARY.md`-г тэр дор нь шинэчил. Хуримтлуулж бүү хүлээ: болмогц нь бич. [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)-ийн хэлбэрийг ашигла.

`GLOSSARY.md`-д хэрэгжүүлэлтийн нарийн зүйл огт байх ёсгүй. `GLOSSARY.md`-г spec, ноорог, эсвэл хэрэгжүүлэлтийн шийдвэрийн сан гэж бүү үз. Энэ бол зөвхөн нэр томъёоны жагсаалт, өөр юу ч биш.

`GLOSSARY.md`-г шинэчилсэн нь кодыг шинэ нэрэнд тааруулж өөрчлөх зөвшөөрөл биш. Тийм өөрчлөлт хэрэгтэй гэж үзвэл эхлээд хэрэглэгчээс асуу.

### ADR-ыг ховор санал болго

ADR (Architecture Decision Record, архитектурын шийдвэрийн тэмдэглэл) үүсгэхийг дараах гурвуулаа үнэн үед л санал болго:

1. **Буцаахад хэцүү**: дараа нь бодлоо өөрчлөх өртөг их
2. **Тайлбаргүй бол гайхмаар**: ирээдүйд уншиж буй хүн "яагаад ингэж хийсэн юм бол?" гэж гайхна
3. **Бодит trade-off-ын үр дүн** (нэгийг авахын тулд нөгөөг золиосолсон): жинхэнэ өөр сонголтууд байсан, тодорхой шалтгаанаар нэгийг нь сонгосон

Гурвын аль нэг нь дутвал ADR бүү бич. [ADR-FORMAT.md](./ADR-FORMAT.md)-ийн хэлбэрийг ашигла.
