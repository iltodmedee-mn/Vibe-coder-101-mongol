# Bug оношлох

Хэцүү bug-т зориулсан дэг журам. Шатыг зөвхөн тодорхой үндэслэлтэй үед л алгас.

Энэ skill нь байгаа зан төлөв эвдэрсэн, буруу ажиллаж байгаа үед зориулагдсан. Зөв ажиллаж байгаа ч өөрөөр болгохыг хүсвэл энэ нь bug биш, feature-ийн өөрчлөлт.

Codebase-ийг судлахдаа `GLOSSARY.md` байвал уншаад холбогдох module-уудын тодорхой дүр зургийг ав. Хөндөж буй хэсгийн ADR-уудыг шалга.

## Нууцыг далдал

Энэ skill-ийн явцад чи команд, гаралт, барьж авсан artifact-уудыг харуулна. **Эхлээд нууц бүрийг далдал**: оронд нь `<REDACTED>` гэж бич. Loop-оо env var ашиглаж бүтээ, тэгвэл credential чиний харуулж буй зүйлд биш, орчинд үлдэнэ. Барьж авсан artifact-д auth header байдаг: зөвхөн дохио агуулсан мөрүүдийг иш тат.

Далдалсан гаралт bug-ийг оношлоход хүрэлцэхгүй бол тэгж хэлээд хэрэглэгчээс асуу.

## 1-р шат: Feedback loop бүтээ

**Энэ skill-ийн гол нь энэ.** Бусад нь механик ажил. Хэрэв чамд bug-ийн **чанга** pass/fail дохио (_яг энэ_ bug дээр улаан болдог) байвал шалтгааныг заавал олно; bisection, hypothesis шалгах, instrumentation бүгд л тэр дохиог ашигладаг. Ийм дохиогүй бол кодыг хичнээн ширтээд ч нэмэргүй.

Энд хэт их хүч зарцуул. **Зоримог бай. Бүтээлч бай. Бууж өгөхөөс татгалз.**

### Loop бүтээх аргууд, ойролцоогоор энэ дарааллаар

1. Bug-т хүрдэг аль ч seam дээрх **унах test**: unit, integration, e2e.
2. Ажиллаж буй dev server руу **curl / HTTP script**.
3. Fixture оролттой **CLI дуудлага**, stdout-ийг зөв гэдэг нь мэдэгдэж буй snapshot-тай diff хийнэ.
4. UI-г удирдаж, DOM/console/network дээр шалгадаг **headless browser script** (Playwright / Puppeteer).
5. **Барьж авсан trace-ийг дахин тогло.** Бодит network request / payload / event log-ийг диск рүү хадгалаад, тэр кодын замаар тусгаарлан дахин ажиллуул.
6. **Нэг удаагийн harness.** Системийн хамгийн бага хэсгийг (нэг service, mock хийсэн dependency) асааж, bug-тэй кодын замыг нэг функцийн дуудлагаар ажиллуул.
7. **Property / fuzz loop.** Bug нь "заримдаа буруу гаралт" бол 1000 санамсаргүй оролт ажиллуулаад алдааны хэлбэрийг хай.
8. **Bisection harness.** Bug хоёр мэдэгдэж буй төлвийн (commit, dataset, хувилбар) хооронд гарсан бол "X төлөвт асаа, шалга, давт"-ыг автоматжуул, тэгвэл `git bisect run` хийж болно.
9. **Differential loop.** Ижил оролтыг хуучин ба шинэ хувилбараар (эсвэл хоёр тохиргоогоор) ажиллуулж гаралтыг diff хий.
10. **HITL bash script** (human-in-the-loop, хүн оролцсон). Хамгийн сүүлийн арга. Хүн заавал дарах ёстой бол `scripts/hitl-loop.template.sh`-ээр _түүнийг_ хөтөл, тэгвэл loop бүтэцтэй хэвээр үлдэнэ. Барьж авсан гаралт чам руу буцаж ирнэ.

**Build эсвэл type алдаа** бол loop аль хэдийн бэлэн: build команд өөрөө. Алдааны мессежийг анхааралтай унш (юу хүлээж, юу авсан), import/type алдааг логикийн алдаанаас өмнө зас, нэг удаад нэг алдаа засаж, засвар бүрийн дараа build-ээ дахин ажиллуул. Энгийн build алдаанд 3–4-р шат ихэвчлэн хэрэггүй.

Зөв feedback loop бүтээвэл bug-ийн 90% нь засагдсан гэсэн үг.

### Loop-оо чангал

Loop-оо бүтээгдэхүүн шиг хар. _Ямар нэг_ loop-тэй болмогц түүнийгээ **чангал**:

- Илүү хурдан болгож болох уу? (Setup-ийг cache хий, хамааралгүй init-ийг алгас, test-ийн хүрээг нарийсга.)
- Дохиог илүү хурц болгож болох уу? ("Унасангүй" биш, яг тэр шинж тэмдгийг шалга.)
- Илүү тогтвортой (deterministic) болгож болох уу? (Цагийг тогтоо, RNG-д seed өг, файлын системийг тусгаарла, network-ийг царцаа.)

30 секундын тогтворгүй loop нь loop байхгүйгээс арай л дээр; 2 секундын тогтвортой loop бол чанга, debug хийх супер хүч.

### Тогтворгүй (non-deterministic) bug

Зорилго нь цэвэр давтагдах тохиолдол биш, **давтагдах магадлалыг өсгөх**. Өдөөгчийг 100 удаа давт, зэрэг ажиллуул, ачаалал нэм, цаг хугацааны цонхыг нарийсга, sleep оруул. 50% давтагддаг bug-ийг debug хийж болно, 1%-ийг болохгүй, тиймээс debug хийж болохуйц болтол магадлалыг өсгөсөөр бай.

### Loop бүтээх үнэхээр боломжгүй үед

Зогсоод үүнийгээ тодорхой хэл. Юу оролдсоноо жагсаа. Хэрэглэгчээс дараахын аль нэгийг гуй: (a) bug давтагддаг орчинд хандах эрх, (b) далдалсан, барьж авсан artifact (HAR файл, log dump, core dump, цагийн тэмдэгтэй дэлгэцийн бичлэг), эсвэл (c) production-д түр instrumentation нэмэх зөвшөөрөл. Loop-гүйгээр hypothesis дэвшүүлэх рүү **бүү** шилж.

### Дуусах шалгуур: улаан болдог чанга loop

1-р шат loop **чанга** бөгөөд **улаан болж чаддаг** үед дуусна: чи **нэг команд** (script-ийн зам, test-ийн дуудлага, curl) нэрлэж чаддаг, түүнийгээ **дор хаяж нэг удаа ажиллуулсан** (дуудлага болон гаралтыг нь далдалж харуул), мөн тэр команд:

- [ ] **Улаан болж чаддаг**: bug-тэй бодит кодын замыг ажиллуулж, **хэрэглэгчийн яг хэлсэн шинж тэмдгийг** шалгадаг, тиймээс энэ bug дээр улаан, засагдсаны дараа ногоон болно. "Алдаагүй ажиллав" биш; _яг энэ bug-ийг барьж_ чаддаг байх ёстой.
- [ ] **Тогтвортой**: ажиллуулах бүрт ижил дүгнэлт (тогтворгүй bug бол дээр дурдсанчлан тогтоосон, өндөр давтагдах магадлал).
- [ ] **Хурдан**: минут биш, секунд.
- [ ] **Agent ажиллуулж чаддаг**: чи хяналтгүйгээр ажиллуулж чадна; хүн зөвхөн `scripts/hitl-loop.template.sh`-ээр оролцоно.

Энэ команд байхгүй байхад онол бүтээхээр код уншиж байгаагаа анзаарвал **зогс: шууд hypothesis руу үсрэх нь энэ skill-ийн яг сэргийлдэг алдаа.** Улаан болж чаддаг команд байхгүй бол 2-р шат ч байхгүй.

## 2-р шат: Давтаж үзүүл + багасга

Loop-оо ажиллуул. Bug гарахад улаан болж байгааг хар.

Баталгаажуул:

- [ ] Loop нь ойролцоо байгаа өөр алдааг биш, **хэрэглэгчийн** тайлбарласан алдааг гаргаж байна. Буруу bug = буруу засвар.
- [ ] Алдаа олон удаа ажиллуулахад давтагдаж байна (эсвэл тогтворгүй bug бол debug хийхэд хангалттай өндөр магадлалтай давтагдаж байна).
- [ ] Яг тэр шинж тэмдгийг (алдааны мессеж, буруу гаралт, удаан хугацаа) барьж авсан, тиймээс дараагийн шатуудад засвар үнэхээр түүнийг шийдсэнийг шалгаж чадна.

### Багасга

Улаан болмогц давтах тохиолдлыг **улаан хэвээр байх хамгийн жижиг хувилбар** болтол багасга. Оролт, дуудагч, тохиргоо, өгөгдөл, алхмуудыг **нэг нэгээр нь** хасаж, хасалт бүрийн дараа loop-оо дахин ажиллуул, зөвхөн алдаанд ачаа үүрч буй зүйлсийг үлдээ.

Яагаад: хамгийн бага давтах тохиолдол 3-р шатанд hypothesis-ийн орон зайг нарийсгана (сэжиглэх хөдөлгөөнт хэсэг цөөрнө), мөн 5-р шатанд цэвэр regression test болно.

**Үлдсэн элемент бүр ачаа үүрч** байвал дууссан: аль нэгийг нь хасахад loop ногоон болно.

Давтаж үзүүлэх **ба** багасгах хоёроо хийхээс өмнө цааш бүү яв.

## 3-р шат: Hypothesis дэвшүүл

Аль нэгийг нь шалгахаас өмнө **эрэмбэлсэн 3–5 hypothesis** гарга. Ганц hypothesis гаргавал хамгийн эхний үнэмшилтэй санаа дээрээ гацна.

Hypothesis бүр **няцаагдах боломжтой** байх ёстой: түүний хүлээгдэх үр дүнг хэл.

> Хэлбэр: "Хэрэв <X> шалтгаан бол <Y-г өөрчлөх> нь bug-ийг алга болгоно / <Z-г өөрчлөх> нь улам дордуулна."

Хүлээгдэх үр дүнг хэлж чадахгүй бол тэр hypothesis зүгээр л мэдрэмж (vibe): хая эсвэл хурцал.

**Шалгахаасаа өмнө эрэмбэлсэн жагсаалтаа хэрэглэгчид харуул.** Тэд ихэвчлэн шууд эрэмбийг өөрчилдөг domain мэдлэгтэй ("бид дөнгөж #3-т өөрчлөлт deploy хийсэн"), эсвэл аль хэдийн үгүйсгэсэн hypothesis-ээ мэддэг. Хямд шалгах цэг, их цаг хэмнэнэ. Үүн дээр бүү гацаж хүлээ; хэрэглэгч хажууд байхгүй бол өөрийн эрэмбээр үргэлжлүүл.

## 4-р шат: Ажиглах цэг суулга (instrument)

Шалгалт бүр 3-р шатны тодорхой нэг хүлээгдэх үр дүнтэй холбогдсон байх ёстой. **Нэг удаад нэг хувьсагч өөрчил.**

Хэрэгслийн давуу эрэмбэ:

1. Орчин дэмждэг бол **debugger / REPL-ээр шалгах**. Нэг breakpoint арван log-оос дээр.
2. Hypothesis-үүдийг ялгадаг хил дээр **онилсон log**.
3. "Бүгдийг log хийгээд grep хийх" хэзээ ч болохгүй.

**Debug log бүрийг** өвөрмөц угтвараар **тэмдэглэ**, жишээ нь `[DEBUG-a4f2]`. Тэгвэл эцэст нь цэвэрлэх нь ганц grep болно. Тэмдэглээгүй log үлддэг; тэмдэглэсэн log устдаг.

**Perf салаа.** Гүйцэтгэлийн уналтад log ихэвчлэн буруу хэрэгсэл. Оронд нь: суурь хэмжилт тогтоо (хугацаа хэмжих harness, `performance.now()`, profiler, query plan), дараа нь bisect хий. Эхлээд хэмж, дараа нь зас.

## 5-р шат: Засвар + regression test

Regression test-ээ **засвараас өмнө** бич, гэхдээ зөвхөн **зөв seam** байгаа үед.

Зөв seam гэдэг нь test нь **бодит bug-ийн хэв маягийг** дуудагдаж буй газар дээр нь гарч байгаагаар нь ажиллуулдаг seam. Боломжтой цорын ганц seam хэт гүехэн бол (bug олон дуудагч шаарддаг байхад нэг дуудагчтай test, bug-ийг өдөөсөн гинжийг давтаж чаддаггүй unit test) тэнд бичсэн regression test худал итгэл төрүүлнэ.

**Зөв seam байхгүй бол энэ нь өөрөө олдвор.** Тэмдэглэ. Codebase-ийн бүтэц bug-ийг түгжихэд саад болж байна. Дараагийн шатанд зориулж үүнийг онцолж хэл.

Зөв seam байвал:

1. Багасгасан давтах тохиолдлыг тэр seam дээр унах test болго.
2. Унаж байгааг нь хар. Хэрэв кодыг эсвэл fixture-ийг өөрчилж улаан болгосон бол, өөрчлөлт үнэхээр орсныг батлахын тулд итгэхээсээ өмнө анхны хуулбартай `diff` хий.
3. Засвараа хий.
4. Давж байгааг нь хар.
5. 1-р шатны feedback loop-оо анхны (багасгаагүй) тохиолдол дээр дахин ажиллуул.

Засвараа хамгийн бага байлга: зөвхөн bug-т хэрэгтэй хэсгийг өөрчил. Засварын явцад refactor хийх, нэр солих, шинэ feature нэмэхгүй.

Засвар test-ийг ногоон болгохгүй бол засвар дээр засвар бүү овоол: hypothesis буруу байна гэсэн үг. 3-р шат руу буцаж жагсаалтаа шинэчил. 2–3 оролдлогын дараа ч ижил алдаа гарсаар, эсвэл засвар бүр шийдсэнээсээ илүү алдаа нэмж байвал зогсоод хэрэглэгчид хэл.

## 6-р шат: Цэвэрлэгээ

Дууссан гэж зарлахаас өмнө заавал:

- [ ] Анхны давтах тохиолдол дахин гарахаа больсон (1-р шатны loop-оо дахин ажиллуул)
- [ ] Regression test давж байна (эсвэл seam байхгүйг тэмдэглэсэн)
- [ ] `[DEBUG-...]` instrumentation бүгд устсан (угтвараар нь `grep` хий)
- [ ] Нэг удаагийн prototype-ууд устсан (эсвэл debug гэж тодорхой тэмдэглэсэн газар руу зөөсөн)
- [ ] Зөв гарсан hypothesis-ийг commit / PR-ийн мессежид бичсэн, тэгвэл дараагийн debug хийх хүн сурна
