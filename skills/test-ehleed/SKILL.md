# Test-ээр эхэлж хөгжүүлэх (TDD)

TDD бол улаан → ногоон (red → green) давталт. Энэ skill бол тэр давталтаас хадгалах үнэ цэнтэй test гаргахад хэрэгтэй лавлах: сайн test гэж юу вэ, test хаана байрлах, анти-паттернууд, давталтын дүрэм. Хэсэг бүр эргэлт бүрт хамаарна: давталтын дараа биш, өмнө нь болон явцад нь харж бай.

Codebase-ийг судлахдаа `GLOSSARY.md` байвал уншаад test-ийн нэр, interface-ийн үгсийг төслийн domain хэлтэй нийцүүл. Хөндөж буй хэсгийн ADR-уудыг хүндэл.

## Сайн test гэж юу вэ

Test нь хэрэгжүүлэлтийн нарийн ширийнийг биш, public interface-ээр дамжуулан зан төлөвийг (behavior) шалгана. Код бүхэлдээ өөрчлөгдөж болно; test өөрчлөгдөх ёсгүй. Сайн test тодорхойлолт (specification) шиг уншигдана: "user can checkout with valid cart" (хэрэглэгч зөв сагстай бол төлбөрөө хийж чадна) гэдэг нь ямар чадвар байгааг яг хэлж өгнө, дотоод бүтцийг тоодоггүй учраас refactor-ийг ч даван туулна.

Жишээг [tests.md](tests.md)-ээс, mock хийх зааврыг [mocking.md](mocking.md)-ээс хар.

## Seam: test хаана байрлах

**Seam** гэдэг нь test хийх public хил: дотор нь гар хийлгүйгээр зан төлөвийг ажигладаг interface. Test зөвхөн seam дээр байрлана, дотоод хэсгийн эсрэг хэзээ ч биш.

**Зөвхөн урьдчилан тохирсон seam дээр test хий.** Ямар ч test бичихээс өмнө test хийх seam-үүдээ бичиж, хэрэглэгчээр батлуул. Батлагдаагүй seam дээр нэг ч test бичихгүй. Бүгдийг test хийх боломжгүй. Seam-ээ урьдчилан тохирсноор test-ийн хүчин чармайлт edge case бүр дээр биш, чухал зам болон нарийн логик дээр төвлөрнө.

Асуу: "Public interface нь юу вэ, аль seam-үүдийг test хийх вэ?" Санал болгож буй seam бүрт юуг барьж, юуг алгасахыг нэг мөрөөр тайлбарла.

Seam-ийн test-ээ сонгохдоо bug ихэвчлэн нуугддаг газруудыг бод: хоосон оролт, хил хязгаарын утга (хамгийн бага/их), алдааны зам (сүлжээ тасрах, хариу ирэхгүй), тусгай тэмдэгт (кирилл үсэг, emoji). Эдгээр нь санал болгох нэр дэвшигчид, бүгдийг нь test хийх жагсаалт биш. Coverage-ийн тоо (test-ээр хамрагдсан кодын хувь) ч мөн зорилго биш, дохио: test-гүй үлдсэн чухал замыг олоход хэрэглэ. 80% орчим нь түгээмэл баримжаа, гэхдээ түүнийг хөөж seam-ээс гадуур test бүү бич.

Тэр interface-ийн хэлбэр өөрөө эргэлзээтэй үед (module хэр гүн байх, seam хаана байх, interface юуг ил гаргах) үгсийн санг авахын тулд Skill tool-ийг "kod-zagvar" гэж дууд. Энэ нь module, interface, depth, seam, adapter, leverage, locality гэсэн нэр томъёоны нийтлэг эх сурвалж. Явуулах session биш, харж лавлах материал.

## Анти-паттернууд

- **Хэрэгжүүлэлттэй уясан**: дотоод хамтрагчдыг mock хийдэг, private method-ийг test хийдэг, эсвэл хажуугийн замаар шалгадаг (interface-ийг ашиглахын оронд database-ээс шууд query хийх). Таних шинж: зан төлөв өөрчлөгдөөгүй байхад refactor хийхэд test эвдэрдэг.
- **Тавтологи**: assertion нь хүлээгдэж буй утгыг код тооцдог шигээ дахин тооцдог (`expect(add(a, b)).toBe(a + b)`, адилхан аргаар гараар гаргасан snapshot, өөртэйгээ тэнцүү гэж шалгасан тогтмол). Ийм test бүтцээрээ давдаг, кодтой хэзээ ч зөрөхгүй. Хүлээгдэж буй утга бие даасан үнэний эх сурвалжаас ирэх ёстой: зөв гэдэг нь мэдэгдэж буй literal, гараар бодсон жишээ, spec.
- **Бие биеэсээ хамааралтай**: нэг test нөгөөгийнхөө үлдээсэн өгөгдөл, төлөв дээр тулгуурладаг. Дангаар нь эсвэл өөр дарааллаар ажиллуулахад эвдэрнэ. Test бүр өгөгдлөө өөрөө бэлдэнэ.
- **Хэвтээ зүсэлт**: эхлээд бүх test-ээ, дараа нь бүх хэрэгжүүлэлтээ бичих. Бөөнөөр бичсэн test-үүд _төсөөлсөн_ зан төлөвийг шалгадаг: хэрэглэгчид харагдах зан төлөвийг биш, юмсын _хэлбэр_-ийг test хийнэ, test-үүд бодит өөрчлөлтөд мэдрэмжгүй болно, хэрэгжүүлэлтээ ойлгохоосоо өмнө test-ийн бүтцээ түгжинэ. Оронд нь **босоо зүсэлтээр** (vertical slice) ажилла: нэг test → нэг хэрэгжүүлэлт → давт. Test бүр өмнөх эргэлтээс сурсан зүйлд хариу өгдөг **tracer bullet** (замаа гэрэлтүүлэн харуулдаг эхний сум) байна.

## Давталтын дүрэм

- **Ногооноос өмнө улаан.** Эхлээд унах test-ээ бич, дараа нь түүнийг давуулахад л хангалттай код бич. Ирээдүйн test-ийг урьдчилж бодох, таамгаар feature нэмэхгүй.
- **Улааныг өөрийн нүдээр хар.** Test-ээ ажиллуулж, зөв шалтгаанаар унаж байгааг шалга: дутуу байгаа зан төлөвөөс болж улаан болох ёстой, syntax алдаа, эвдэрсэн setup, дутуу dependency-ээс болж биш. Бичсэн ч ажиллуулаагүй test улаанд тооцогдохгүй. Кодоо бичсэний дараа яг тэр test-ээ дахин ажиллуулж ногоон болсныг хар.
- **Нэг удаад нэг зүсэлт.** Эргэлт бүрт нэг seam, нэг test, нэг хамгийн бага хэрэгжүүлэлт.
- **Ногоон бүрийн дараа commit хийвэл сайн хадгалах цэг болно.** Дараагийн алхам буруу явбал тэнд нь буцаж ирнэ.
- **Refactor давталтын нэг хэсэг биш.** Энэ нь red → green хэрэгжүүлэлтийн эргэлтэд биш, review шатанд хамаарна (`kod-hyana` skill-ийг хар).
