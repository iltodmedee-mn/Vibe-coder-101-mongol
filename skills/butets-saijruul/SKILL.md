# Кодын бүтцийг сайжруулах

Архитектурын саадыг (friction) илрүүлж, **гүнзгийрүүлэх боломжуудыг** санал болго: shallow module-уудыг deep болгох refactor. Зорилго нь test хийхэд хялбар, AI-д ойлгомжтой код.

Энэ command төслийн domain model-оос мэдээлэл _авч_, нийтлэг дизайны хэл дээр тулгуурлана:

- Архитектурын нэр томъёо (**module**, **interface**, **depth**, **seam**, **adapter**, **leverage**, **locality**) ба зарчмуудыг (deletion test, "interface бол test-ийн гадаргуу", "нэг adapter = таамаг seam, хоёр = жинхэнэ") авахын тулд Skill tool-ыг "kod-zagvar" гэж дууд. Санал бүрт эдгээр нэр томъёог яг хэрэглэ, "component", "service", "API", "boundary" руу бүү гулс.
- `GLOSSARY.md` дахь domain-ий хэл сайн seam-уудад нэр өгнө; `docs/adr/` дахь ADR-ууд энэ command дахин маргах ёсгүй шийдвэрүүдийг бүртгэнэ.

## Явц

### 1. Судал

**Хайхаасаа өмнө хүрээгээ тогтоо: YAGNI** (одоо хэрэггүй зүйлийг бүү хий). Module-ийг гүнзгийрүүлэх нь цаашдын өөрчлөлтийг хялбар болгодгоороо үр ашгаа өгдөг тул саяхан өөрчлөгдсөн хэсгүүдэд илүү жин өг. Хаана харахаа харахаасаа өмнө шийд:

- Хэрэглэгч чиглэл заасан бол (module, дэд систем, өвдөж буй газар) түүнийг ав, доорх дүгнэлтийг алгас.
- Үгүй бол commit-ийн түүхийг (`git log --oneline`) нэлээд хойш гүйлгэж, codebase-ийн халуун цэгүүдийг ол: байнга гарч ирдэг файл, хэсгүүд. Эхлээд тэр замууд руу анхаар. Өөрчлөлтүүд тодорхой халуун цэггүй тархсан бол хайх хүрээгээ өргөсгө.

Хүрч буй хэсгийнхээ domain glossary (`GLOSSARY.md`) ба ADR-уудыг эхэлж унш.

Дараа нь codebase-ийг тойрон судлах sub-agent-ыг шинэ context window-оор эхлүүл. Хатуу дүрэм бүү дага; чөлөөтэй судалж, саад мэдэрсэн газраа тэмдэглэ:

- Нэг ойлголтыг ойлгохын тулд олон жижиг module-ийн хооронд үсчих хэрэгтэй газар хаана байна?
- Хаана module-ууд **shallow** буюу interface нь implementation-тэйгээ бараг адил нарийн байна?
- Хаана цэвэр function-уудыг зөвхөн test хийхийн тулд салгасан боловч жинхэнэ bug-ууд нь тэднийг хэрхэн дууддагт нуугдаж байна (**locality** байхгүй)?
- Хаана хоорондоо нягт холбогдсон module-ууд seam-ээ давж нэвчиж байна?
- Codebase-ийн аль хэсэг test-гүй, эсвэл одоогийн interface-ээрээ test хийхэд хэцүү байна?

Shallow гэж сэжиглэсэн бүх зүйлд **deletion test** хий: устгавал нарийн төвөгтэй байдал нэг газарт төвлөрөх үү, эсвэл зүгээр л нүүх үү? "Тийм, төвлөрнө" гэдэг нь чиний хайж буй дохио.

### 2. Нэр дэвшигчдийг HTML тайлангаар танилцуул

Repo-д юу ч орохгүйн тулд бие даасан HTML файлыг үйлдлийн системийн түр folder-т бич. Түр folder-ийг `$TMPDIR`-ээс ав, байхгүй бол `/tmp` (Windows дээр `%TEMP%`), мөн ажиллуулалт бүр шинэ файлтай байхаар `<tmpdir>/architecture-review-<timestamp>.html` руу бич. Хэрэглэгчид нээж өг (Linux дээр `xdg-open <path>`, macOS дээр `open <path>`, Windows дээр `start <path>`) ба бүтэн замыг нь хэл.

Тайлан layout, загварт **CDN-ээр Tailwind**, граф/урсгал/дарааллыг найдвартай харуулах газар диаграммд **CDN-ээр Mermaid** хэрэглэнэ. Mermaid-ийг гараар хийсэн CSS/SVG дүрслэлтэй холь: хамаарал нь граф хэлбэртэй бол (call graph, хамаарал, дараалал) Mermaid, сэтгүүлийн маягийн зүйл хүсвэл (масс диаграмм, хөндлөн огтлол, хумигдах animation) гараар хийсэн div/SVG хэрэглэ. Нэр дэвшигч бүр **өмнө / дараах дүрслэлтэй** байна. Харагдахуйц бай.

Нэр дэвшигч бүрт карт зур:

- **Файлууд**: аль файл/module-ууд оролцож байна
- **Асуудал**: одоогийн архитектур яагаад саад үүсгэж байна
- **Шийдэл**: юу өөрчлөгдөхийг энгийн үгээр
- **Ашиг**: locality ба leverage-ийн үүднээс, мөн test хэрхэн сайжрах
- **Өмнө / Дараах диаграмм**: зэрэгцээ, гараар зурсан, shallow байдал ба гүнзгийрүүлэлтийг харуулсан
- **Зөвлөмжийн хүч**: `Хүчтэй`, `Судлах нь зүйтэй`, `Таамаг`-ийн аль нэг, badge хэлбэрээр

Тайлангаа **Шилдэг зөвлөмж** хэсгээр төгсгө: аль нэр дэвшигчээс эхлэх, яагаад.

**Domain-д GLOSSARY.md-ийн, архитектурт `/kod-zagvar`-ийн нэр томъёог хэрэглэ.** `GLOSSARY.md` "Order"-ийг тодорхойлсон бол "FooBarHandler" ч биш, "Order service" ч биш, "Order intake module" гэж ярь.

**ADR-тай зөрчилдөх нь**: нэр дэвшигч одоо байгаа ADR-тай зөрчилдвөл саад нь ADR-ийг эргэн харах хэмжээнд бодитой үед л гарга. Картад тод тэмдэглэ (жишээ нь анхааруулгын хайрцаг: _"ADR-0007-той зөрчилдөж байгаа ч дахин нээх нь зүйтэй, учир нь…"_). ADR хориглосон онолын бүх refactor-ыг бүү жагсаа.

Бүтэн HTML scaffold, диаграммын хэв маяг, загварын зөвлөмжийг [HTML-REPORT.md](HTML-REPORT.md)-ээс үз.

Interface-ийг одоохондоо бүү санал болго. Файл бичигдсэний дараа хэрэглэгчээс асуу: "Эдгээрээс алийг нь судалмаар байна?"

### 3. Шалгалтын давталт

Хэрэглэгч нэр дэвшигч сонгомогц Skill tool-ыг "shalgalt" гэж дуудаж, шийдвэрийн модоор хамт алх: хязгаарлалт, хамаарал, гүнзгийрүүлсэн module-ийн хэлбэр, seam-ийн ард юу байх, аль test-үүд үлдэх.

Шийдвэр тодорхой болох тусам хажуугийн ажлуудыг тэр дор нь хий; domain model-оо шинэчлэгдсэн байлгахын тулд Skill tool-ыг "domain-zagvar" гэж дууд:

- **Гүнзгийрүүлсэн module-ийг `GLOSSARY.md`-д байхгүй ойлголтоор нэрлэж байна уу?** Тэр нэр томъёог `GLOSSARY.md`-д нэм. Файл байхгүй бол хэрэгтэй болсон үед нь үүсгэ.
- **Ярианы явцад бүрхэг нэр томъёог тодруулж байна уу?** `GLOSSARY.md`-г тэр дор нь шинэчил.
- **Хэрэглэгч нэр дэвшигчийг жинтэй шалтгаанаар татгалзаж байна уу?** ADR санал болго: _"Ирээдүйн архитектурын хяналт үүнийг дахин санал болгохгүйн тулд ADR болгож бүртгэх үү?"_ Тэр шалтгаан ирээдүйн судлаачид ижил зүйлийг дахин санал болгохоос сэргийлэхэд үнэхээр хэрэгтэй үед л санал болго; түр зуурын ("одоохондоо хэрэггүй") ба өөрөө ойлгомжтой шалтгааныг алгас.
- **Гүнзгийрүүлсэн module-д өөр interface-үүдийг судлах уу?** Skill tool-ыг "kod-zagvar" гэж дуудаж, түүний design-it-twice зэрэгцээ sub-agent-ийн хэв маягийг хэрэглэ.
