# Agent brief бичих

Agent brief бол issue эсвэл PR `ready-for-agent` руу шилжихэд GitHub issue эсвэл PR дээр бичдэг бүтэцтэй сэтгэгдэл. AFK agent (хүн хажууд нь байхгүй үед бие даан ажилладаг agent) яг үүнийг үндсэн тодорхойлолт болгож ажиллана. Анхны текст ба хэлэлцүүлэг нь зөвхөн context: agent brief бол гэрээ.

Brief нь **agent юу хийх ёстойг** хэлнэ, энэ нь хоёр төрөлд хоёуланд нь хамаарна: issue бол өөрчлөлтийг эхнээс нь бүтээх; PR бол *одоо байгаа diff дээр* юу үлдсэн: дуусгах, дутууг нөхөх, review-ийн санааг шийдэх. Зарчим нь аль алинд нь ижил; доорх PR-ийн жишээ ялгааг харуулна.

## Зарчмууд

### Нарийвчлалаас илүү удаан хүчинтэй байх нь чухал

Issue `ready-for-agent` дээр хэдэн өдөр, долоо хоног хүлээж болно. Энэ хооронд код өөрчлөгдөнө. Файлууд нэр солигдох, зөөгдөх, refactor хийгдсэн ч brief ашигтай хэвээр байхаар бич.

- Interface, type, үйлдлийн гэрээг (behavioral contract) **тайлбарла**
- Agent хайх эсвэл өөрчлөх ёстой тодорхой type, функцийн signature, config-ийн бүтцийг **нэрлэ**
- Файлын зам **бүү** заа: тэд хуучирдаг
- Мөрийн дугаар **бүү** заа
- Одоогийн хэрэгжүүлэлтийн бүтэц хэвээр үлдэнэ гэж **бүү** тооц

### Алхам биш, үйлдлийг тайлбарла

Систем **юу** хийх ёстойг тайлбарла, **яаж** хэрэгжүүлэхийг биш. Agent кодыг шинээр судалж, хэрэгжүүлэлтийн шийдвэрээ өөрөө гаргана.

- **Сайн:** "`SkillConfig` type нь `CronExpression` төрлийн, заавал биш `schedule` талбар хүлээн авах ёстой"
- **Муу:** "src/types/skill.ts-г нээгээд 42-р мөрөнд schedule талбар нэм"
- **Сайн:** "Хэрэглэгч `/angil`-ыг аргументгүй ажиллуулахад анхаарал хэрэгтэй issue-уудын хураангуйг харах ёстой"
- **Муу:** "Үндсэн handler функцэд switch statement нэм"

### Бүрэн acceptance criteria

Agent хэзээ дууссанаа мэдэх хэрэгтэй. Agent brief бүр тодорхой, test хийж болох acceptance criteria-тай (хүлээн авах шалгуур) байх ёстой. Шалгуур бүрийг тусад нь шалгаж болдог байх ёстой.

- **Сайн:** "`gh issue list --label needs-triage` ажиллуулахад анхны ангилалд орсон issue-ууд гарч ирнэ"
- **Муу:** "Ангилал зөв ажиллах ёстой"

### Хамрах хүрээг тодорхой заах

Юу хамрах хүрээнд ороогүйг хэл. Ингэснээр agent шаардлагагүй нэмэлт хийх, эсвэл хөрш feature-уудын талаар таамаг дэвшүүлэхээс сэргийлнэ.

## Загвар

```markdown
## Agent Brief

**Ангилал:** bug / enhancement
**Хураангуй:** юу хийх ёстойг нэг мөрөөр

**Одоогийн үйлдэл:**
Одоо юу болж байгааг тайлбарла. Bug бол энэ нь эвдэрсэн үйлдэл.
Enhancement бол шинэ feature-ийн суурилах одоогийн байдал.

**Хүссэн үйлдэл:**
Agent ажлаа дуусгасны дараа юу болох ёстойг тайлбарла.
Онцгой тохиолдол (edge case) ба алдааны нөхцөлийг тодорхой бич.

**Гол interface-үүд:**
- `TypeName`: юу өөрчлөгдөх, яагаад
- `functionName()`-ийн буцаах type: одоо юу буцаадаг, юу буцаах ёстой
- Config-ийн бүтэц: шинээр хэрэгтэй тохиргоо

**Acceptance criteria:**
- [ ] Тодорхой, test хийж болох 1-р шалгуур
- [ ] Тодорхой, test хийж болох 2-р шалгуур
- [ ] Тодорхой, test хийж болох 3-р шалгуур

**Хамрах хүрээнээс гадуур:**
- Энэ issue-д өөрчлөх, шийдэх ёсгүй зүйл
- Холбоотой мэт боловч тусдаа хөрш feature
```

## Жишээнүүд

### Сайн agent brief (bug)

```markdown
## Agent Brief

**Ангилал:** bug
**Хураангуй:** Skill-ийн description-ийг таслахдаа үгийн дундуур тасалж, эвдэрхий үр дүн гаргадаг

**Одоогийн үйлдэл:**
Skill-ийн description 1024 тэмдэгтээс урт бол үгийн хилийг үл харгалзан
яг 1024 тэмдэгт дээр тасалдаг. Үүнээс болж description үгийн дундуур
дуусдаг (жишээ нь "Use when the user wants to confi").

**Хүссэн үйлдэл:**
1024 тэмдэгтээс өмнөх сүүлийн үгийн хил дээр тасалж, тасалсныг
илтгэх "..."-ийг ард нь залгана.

**Гол interface-үүд:**
- `SkillMetadata` type-ийн `description` талбар: type өөрчлөх шаардлагагүй,
  гэхдээ түүнийг бөглөдөг шалгах/боловсруулах логик үгийн хилийг
  хүндэтгэх ёстой
- SKILL.md-ийн эхэн дэх YAML хэсгийг (`---` хооронд) уншиж description-ийг гаргаж авдаг аливаа функц

**Acceptance criteria:**
- [ ] 1024 тэмдэгтээс богино description өөрчлөгдөхгүй
- [ ] 1024 тэмдэгтээс урт description-ийг 1024 тэмдэгтээс өмнөх
      сүүлийн үгийн хил дээр тасална
- [ ] Тасалсан description "..."-ээр төгсөнө
- [ ] "..."-ийг оруулаад нийт урт 1024 тэмдэгтээс хэтрэхгүй

**Хамрах хүрээнээс гадуур:**
- 1024 тэмдэгтийн хязгаарыг өөрөө өөрчлөх
- Олон мөртэй description-ийг дэмжих
```

### Сайн agent brief (enhancement)

```markdown
## Agent Brief

**Ангилал:** enhancement
**Хураангуй:** Татгалзсан feature хүсэлтүүдийг бүртгэх `.out-of-scope/` folder-ийн дэмжлэг нэмэх

**Одоогийн үйлдэл:**
Feature хүсэлтийг татгалзахад issue-г `wontfix` label, сэтгэгдэлтэйгээр
хаадаг. Шийдвэр, шалтгааны байнгын бүртгэл байхгүй. Ирээдүйд ижил төстэй
хүсэлт ирэхэд maintainer өмнөх хэлэлцүүлгийг санах эсвэл хайх хэрэгтэй болдог.

**Хүссэн үйлдэл:**
Татгалзсан feature хүсэлтүүдийг `.out-of-scope/<concept>.md` файлуудад
бичиж, шийдвэр, шалтгаан, тухайн feature-ийг хүссэн бүх issue-ийн
холбоосыг хадгална. Шинэ issue ангилахдаа эдгээр файлтай тулгана.

**Гол interface-үүд:**
- `.out-of-scope/` дахь markdown файлын формат: файл бүр `# Ойлголтын нэр`
  гарчиг, `**Шийдвэр:**` мөр, `**Шалтгаан:**` мөр, issue-ийн холбоостой
  `**Өмнөх хүсэлтүүд:**` жагсаалттай байна
- Ангиллын workflow нь эхэндээ бүх `.out-of-scope/*.md` файлыг уншиж,
  ирсэн issue-г тэдгээртэй ойлголтын төстэй байдлаар тулгана

**Acceptance criteria:**
- [ ] Feature-ийг wontfix гэж хаахад `.out-of-scope/` дотор файл үүсэх/шинэчлэгдэх
- [ ] Файлд шийдвэр, шалтгаан, хаагдсан issue-ийн холбоос байна
- [ ] Таарах `.out-of-scope/` файл аль хэдийн байвал давхар файл үүсгэхгүй,
      шинэ issue-г түүний "Өмнөх хүсэлтүүд" жагсаалтад нэмнэ
- [ ] Ангиллын үеэр байгаа `.out-of-scope/` файлуудыг шалгаж, шинэ issue
      өмнөх татгалзалтай таарвал гаргаж харуулна

**Хамрах хүрээнээс гадуур:**
- Автоматаар тулгах (таарлыг хүн батална)
- Өмнө татгалзсан feature-уудыг дахин нээх
- Bug report (зөвхөн enhancement-ийн татгалзал `.out-of-scope/` руу орно)
```

### Сайн agent brief (PR)

PR-ийн хувьд "Одоогийн үйлдэл" нь diff-ийн байдлыг тайлбарлах бөгөөд brief нь agent-аас эхнээс нь бүтээхийг биш, дуусгах эсвэл засахыг хүснэ.

```markdown
## Agent Brief

**Ангилал:** enhancement
**Хураангуй:** `angil list`-д хувь нэмэр оруулагчийн нэмсэн `--json` гаралтын flag-ийг дуусгах

**Одоогийн үйлдэл:**
PR нь issue-уудын жагсаалтыг JSON болгодог `--json` flag нэмж байна. Хэвийн
зам ажилладаг бөгөөд diff нь төслийн командын бүтэцтэй таарч байна. Хоёр
дутуу үлдсэн: алдаанууд хүнд зориулсан текстээр (JSON биш) хэвлэгдсээр байна,
шинэ flag-д test огт байхгүй.

**Хүссэн үйлдэл:**
`--json`-той үед бүх гаралт (алдааг оруулаад) stdout дээр зөв бүтэцтэй JSON
байна, командын exit code өөрчлөгдөхгүй. Flag байхгүй үед хүнд зориулсан
одоогийн гаралт хөндөгдөхгүй.

**Гол interface-үүд:**
- `--json`-той үед командын алдааны зам энгийн текст алдааны оронд
  `{ "error": string }` гаргах ёстой
- PR-ийн аль хэдийн нэмсэн serializer-ийг дахин ашигла; хоёр дахийг бүү нэм

**Acceptance criteria:**
- [ ] `angil list --json` амжилттай болон алдааны аль алинд зөв JSON гаргана
- [ ] Exit code нь JSON-гүй командтай ижил
- [ ] `--json`-ийн амжилттай гаралт ба нэг алдааны тохиолдлыг test хамарна
- [ ] Үндсэн (JSON-гүй) гаралт byte бүрээрээ өөрчлөгдөхгүй

**Хамрах хүрээнээс гадуур:**
- Өөр ямар нэг командад `--json` нэмэх
- PR-ийн аль хэдийн тодорхойлсон амжилттай payload-ийн JSON бүтцийг өөрчлөх
```

### Муу agent brief

```markdown
## Agent Brief

**Хураангуй:** Ангиллын bug-ийг засах

**Юу хийх:**
Ангиллын тэр юм эвдэрчихсэн. Үндсэн файлыг хараад зас.
150-р мөрийн орчим байгаа функцэд асуудал байна.

**Өөрчлөх файлууд:**
- src/angil/handler.ts (150-р мөр)
- src/types.ts (42-р мөр)
```

Энэ яагаад муу вэ:
- Ангилал байхгүй
- Бүрхэг тайлбар ("ангиллын тэр юм эвдэрчихсэн")
- Хуучирдаг файлын зам, мөрийн дугаар заасан
- Acceptance criteria байхгүй
- Хамрах хүрээний хил байхгүй
- Одоогийн ба хүссэн үйлдлийн тайлбар байхгүй
