# Хамрах хүрээнээс гадуурх зүйлсийн мэдлэгийн сан

Repo дахь `.out-of-scope/` folder нь татгалзсан feature хүсэлтүүдийн байнгын бүртгэлийг хадгална. Хоёр зорилготой:

1. **Төслийн санах ой**: feature-ийг яагаад татгалзсаныг хадгалж, issue хаагдахад шалтгаан нь алга болохгүй
2. **Давхардлаас сэргийлэх**: шинэ issue өмнөх татгалзалтай таарвал skill дахин маргалгүйгээр өмнөх шийдвэрийг гаргаж ирнэ

## Folder-ийн бүтэц

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

Issue бүрт биш, **ойлголт** бүрт нэг файл. Ижил зүйл хүссэн олон issue-г нэг файлд бүлэглэнэ.

## Файлын формат

Файлыг database-ийн бичлэг гэхээсээ илүү богино дизайны баримт шиг, чөлөөтэй, уншихад хялбар хэв маягаар бич. Анх удаа уншиж буй хүнд шалтгаан нь ойлгомжтой, хэрэгтэй байхаар догол мөр, кодын жишээ, бодит жишээ ашигла.

````markdown
# Dark mode

Энэ төсөл dark mode болон хэрэглэгчийн theme-ийг дэмждэггүй.

## Яагаад хамрах хүрээнээс гадуур вэ

Render хийх pipeline нь `ThemeConfig`-д тодорхойлсон ганц өнгөний палитр
байна гэж үздэг. Олон theme дэмжихийн тулд дараах зүйлс хэрэгтэй:

- Бүх component-ийн модыг ороосон theme context provider
- Component бүрт theme-ээс хамаарч style тодорхойлох
- Хэрэглэгчийн theme сонголтыг хадгалах давхарга

Энэ бол архитектурын томоохон өөрчлөлт бөгөөд контент бичихэд төвлөрсөн
төслийн чиглэлтэй нийцэхгүй. Theme бол гаралтыг өөрсдийн бүтээгдэхүүнд
суулгадаг эсвэл дахин түгээдэг хэрэглэгчдийн асуудал.

```ts
// Одоогийн ThemeConfig interface нь ажиллаж байх үед солиход зориулагдаагүй:
interface ThemeConfig {
  colors: ColorPalette; // ганц палитр, build хийх үед тодорхойлогддог
  fonts: FontStack;
}
```

## Өмнөх хүсэлтүүд

- #42: "Dark mode дэмжлэг нэмэх"
- #87: "Хүртээмжид зориулсан шөнийн theme"
- #134: "Бараан theme-ийн сонголт"
````

### Файлыг нэрлэх

Ойлголтод зориулсан богино, тодорхой kebab-case нэр ашигла: `dark-mode.md`, `plugin-system.md`, `graphql-api.md`. Folder-ийг гүйлгэж харж буй хүн файлыг нээлгүйгээр юуг татгалзсаныг ойлгохоор нэр нь танигдахуйц байх ёстой.

### Шалтгааныг бичих

Шалтгаан нь бодитой байх ёстой: "бид үүнийг хүсэхгүй" биш, яагаад гэдэг нь. Сайн шалтгаан дараахыг иш татна:

- Төслийн хамрах хүрээ эсвэл философи ("Энэ төсөл X-д төвлөрдөг; theme бол үүнийг ашиглагчдын асуудал")
- Техникийн хязгаарлалт ("Үүнийг дэмжихэд Y хэрэгтэй, энэ нь манай Z архитектуртай зөрчилдөнө")
- Стратегийн шийдвэр ("Бид B-ийн оронд A-г сонгосон, учир нь...")

Шалтгаан удаан хүчинтэй байх ёстой. Түр зуурын нөхцөлийг ("бид одоо хэтэрхий завгүй байна") бүү иш тат; эдгээр нь жинхэнэ татгалзал биш, хойшлуулалт.

## `.out-of-scope/`-г хэзээ шалгах вэ

Ангиллын үеэр (1-р алхам: Мэдээлэл цуглуул) `.out-of-scope/` дахь бүх файлыг унш. Шинэ issue-г үнэлэхдээ:

- Хүсэлт нь одоо байгаа хамрах хүрээнээс гадуурх ойлголттой таарч байгаа эсэхийг шалга
- Түлхүүр үгээр биш, ойлголтын төстэй байдлаар тулга: "шөнийн theme" нь `dark-mode.md`-тэй таарна
- Таарвал maintainer-т гаргаж харуул: "Энэ `.out-of-scope/dark-mode.md`-тэй төстэй байна. Бид үүнийг өмнө нь [шалтгаан] гэж татгалзсан. Чи одоо ч мөн адил бодож байна уу?"

Maintainer дараахын аль нэгийг хийж болно:

- **Батлах**: шинэ issue-г одоо байгаа файлын "Өмнөх хүсэлтүүд" жагсаалтад нэмээд хаана
- **Эргэн харах**: хамрах хүрээнээс гадуурх файлыг устгах эсвэл шинэчилж, issue ердийн ангиллаар явна
- **Санал зөрөх**: issue-ууд холбоотой ч өөр зүйл тул ердийн ангиллаар үргэлжилнэ

## `.out-of-scope/` руу хэзээ бичих вэ

Зөвхөн **enhancement** (bug биш) `wontfix` гэж *татгалзагдсан* үед. Энэ нь enhancement PR-д issue-тэй яг адил хамаарна: татгалзсан PR-ийг энд бүртгэснээр ижил хүсэлт шинэ код болж буцаж ирэхгүй.

Аль хэдийн **хэрэгжсэн** учраас `wontfix`-ээр хаагдсан бол энд **бүү** бич. Энэ бол татгалзсан биш, бүтээгдсэн feature; үүнийг бүртгэвэл давхардлын шалгалтыг худал татгалзлаар бохирдуулна. Харин хаах сэтгэгдэлд feature аль хэдийн хаана байгааг заа.

Дараалал:

1. Maintainer feature хүсэлтийг хамрах хүрээнээс гадуур гэж шийднэ
2. Таарах `.out-of-scope/` файл байгаа эсэхийг шалга
3. Байвал: шинэ issue-г "Өмнөх хүсэлтүүд" жагсаалтад нэм
4. Байхгүй бол: ойлголтын нэрээр шинэ файл үүсгэж, шийдвэр, шалтгаан, анхны хүсэлтийг бич
5. Issue дээр шийдвэрийг тайлбарлаж, `.out-of-scope/` файлыг дурдсан сэтгэгдэл бич
6. Issue-г `wontfix` label-тай хаа

## Хамрах хүрээнээс гадуурх файлыг шинэчлэх эсвэл устгах

Maintainer өмнө татгалзсан ойлголтын талаар бодлоо өөрчилвөл:

- `.out-of-scope/` файлыг устга
- Skill хуучин issue-уудыг дахин нээх шаардлагагүй; тэд түүхэн бичлэг
- Дахин бодоход хүргэсэн шинэ issue ердийн ангиллаар явна
