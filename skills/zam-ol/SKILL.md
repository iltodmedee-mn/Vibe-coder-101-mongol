Бүдэг санаа ирлээ: нэг agent session-д багтахааргүй том, бас манан дунд байна, эндээс **очих газар** (destination) хүрэх зам хараахан харагдахгүй. Зам олох гэдэг нь очих газар руу шууд дайрах биш, тэр замыг олох тухай. Энэ skill замыг repo-гийн issue tracker дээр **хуваалцсан map** (газрын зураг) болгон зурж, дараа нь түүний **шийдвэрийн ticket**-үүдийг (хариулт нь шийдвэр байдаг асуултууд; барих ажлын хэсгүүд биш) зам тодорхой болтол нэг нэгээр нь шийднэ.

Очих газар ажил бүрт өөр, түүнийг нэрлэх нь map зурах эхний алхам: энэ нь ticket бүрийг тодорхойлно. Энэ нь цааш дамжуулж, сайжруулах spec, төлөвлөлт эхлэхээс өмнө тогтоох шийдвэр, эсвэл data бүтцийн шилжүүлэлт шиг газар дээр нь хийх өөрчлөлт байж болно. Map ямар ч салбарт тохирно: инженерийн ажил, сургалтын контент, энэ хэлбэрт таарах юу ч.

## Төлөвлө, бүү хий

Zam-ol анхдагчаар **төлөвлөлт**: ticket бүр нэг шийдвэр гаргана, зам тодорхой болж, хэн нэгэн очиж ажлаа хийхээс өмнө шийдэх юм үлдээгүй үед map дуусна. Ажлаа шууд хийчихмээр санагдах нь ихэвчлэн map-ын захад хүрч, ажлыг дамжуулах цаг болсны дохио. Тухайн ажил **Тэмдэглэл** хэсэгтээ үүнийг өөрчилж, гүйцэтгэлийг map дотор оруулж болно; тэгээгүй бол үр дүн биш, шийдвэр гарга.

## Нэрээр нь дурд

Map, ticket бүр issue тул **нэр**тэй: гарчиг нь. Хүний уншдаг бүх зүйлд (тайлбар, map-ын Гаргасан шийдвэрүүд) нэрээр нь дурд, хэзээ ч зөвхөн id, дугаар, slug-аар биш. `#42, #43, #44` гэсэн хана уншигдахгүй; нэр шууд ойлгогдоно. Id болон URL алга болохгүй: нэр холбоосоо ороож явна, тэд нэрийн _дотор_ явна, нэрийг орлохгүй.

## Map

Map бол энэ repo-гийн issue tracker дээрх `zam-ol:map` label-тай ганц issue, гол баримт. Түүний ticket-үүд нь map-ын child issue-нууд.

Map бол агуулах биш, **индекс**. Гаргасан шийдвэрүүдийг жагсааж, дэлгэрэнгүйг нь агуулсан ticket руу заана; шийдвэр яг нэг газар, өөрийн ticket-дээ амьдардаг тул map түүнийг дахин бичихгүй, зөвхөн товчлоод холбоно.

**Map, түүний child ticket-үүд, хориг (blocking), frontier-ийн query физикээр хаана байх нь tracker-аас хамаарна.** Issue tracker чамд өгөгдсөн байх ёстой. Үгүй бол хэрэглэгчид `/tohiruul` ажиллуулахыг хэл. _Энэ_ repo эдгээрийг яаж илэрхийлдгийг tracker баримтын `/zam-ol`-д зориулсан хэсгээс хар. Tracker өгөгдөөгүй бол local-markdown tracker-ийг анхдагчаар ашигла.

Бүх map бага нарийвчлалтайгаар, session бүрт нэг удаа ачаалагдана. Нээлттэй ticket-үүд энд **жагсаагдахгүй**: тэд нээлттэй child issue-нууд тул query-гээр олдоно.

### Ticket-үүд

Ticket бүр map-ын **child issue**; tracker-ийн issue id нь түүний таних тэмдэг. Бие нь асуулт, нэг 100K token agent session-д багтах хэмжээтэй:

```markdown
## Асуулт

<энэ ticket-ийн шийдэх шийдвэр эсвэл судалгаа>
```

Ticket бүр `zam-ol:<type>` label-тай: `research`, `prototype`, `grilling`, `task`-ын аль нэг (доорх **Ticket-ийн төрлүүд**-ийг хар). `zam-ol:` label-ууд бол map болон түүний ticket-үүдийн цорын ганц label, `ready-for-agent` шиг triage label хэзээ ч биш: эдгээр нь хэрэгжүүлэх ажил биш, шийдвэрүүд.

Session ticket-ийг **эзэмшихдээ** (claim) map-ыг удирдаж буй хүнд assign хийнэ, ямар ч ажлаас **өмнө**, ингэснээр зэрэг ажиллаж буй бусад session түүнийг алгасна. Тэр assignee _бол_ эзэмшил: нээлттэй, assign хийгдээгүй ticket эзэмшигдээгүй.

Хориг нь tracker-ийн **native** хамаарлын холбоосыг ашиглана: энэ нь frontier-ийг tracker-ийн өөрийн UI дээр _нүдээр_ харуулдаг учраас чухал, хүн map-ыг нээлгүйгээр юуг авч болохыг харна. Native хориг байхгүй tracker л биед нь бичих тохиролцоо руу буцна. Ticket-ийг хорьж буй бүх ticket хаагдсан үед тэр **хоригоос гарна** (unblocked); **frontier** бол нээлттэй, хоригоос гарсан, эзэмшигдээгүй child-ууд: мэдэгдэж буй зүйлийн зах.

Хариулт биеийн хэсэг биш; шийдэгдэх үед бичигдэнэ (доорх **Map-аар явах**-ыг хар). Ticket шийдэх явцад үүссэн зүйлсийг issue-ээс холбоно, наахгүй.

## Ticket-ийн төрлүүд

Ticket бүр **HITL** (human in the loop: өөрийнхөө өмнөөс ярьдаг хүнтэй _хамт_ хийдэг) эсвэл **AFK** (agent ганцаараа хийдэг) байна. HITL ticket зөвхөн тэр амьд яриагаар л шийдэгдэнэ; agent хэзээ ч хүний талыг орлохгүй (өөрийнхөө асуултад өөрөө хариулдаг shalgalt agent энэ дүрмийг зөрчсөн).

- **Research** (AFK): Шийдвэр хүлээж буй баримтыг олохын тулд documentation, гуравдагч талын API, эсвэл мэдлэгийн сан шиг local эх сурвалж унших. Skill tool-оор `sudal`-ыг дууддаг subagent шийднэ. Одоогийн ажлын folder-оос гадуурх мэдлэг хэрэгтэй үед ашигла.
- **Prototype** (HITL): Хариу үйлдэл үзүүлэх хямд, бүдүүлэг, бодит зүйл (тойм, бүдүүлэг хувилбар, stub, эсвэл UI/logic код) хийж яриаг илүү бодитой болгох: Skill tool-оор `turshilt`-ыг дууд. Prototype-ийг asset болгож холбоно. "Яаж харагдах вэ" эсвэл "яаж ажиллах вэ" гол асуулт бол ашигла.
- **Grilling** (HITL): Яриа. Анхдагч тохиолдол. Skill tool-ыг үргэлж хоёр удаа дууд: `shalgalt` болон `domain-zagvar`.
- **Task** (HITL эсвэл AFK): _Шийдвэр_ гаргахаас өмнө заавал хийх гар ажил: шийдэх, prototype хийх, судлах юм алга, гэхдээ үүнийг хийтэл яриа гацна. API-г нь үнэлэхийн тулд үйлчилгээнд бүртгүүлэх, хандалт тохируулах, data-гийн хэлбэрийг харахын тулд түүнийг зөөх. Энэ бол шийдэх биш _хийдэг_ цорын ганц төрөл; очих газрыг хүргэснээр биш, шийдвэрийг гацаанаас гаргаснаар байр сууриа олдог. Agent чадах газраа ганцаараа хийнэ (AFK); үгүй бол хүнд яг тодорхой checklist өгнө (HITL). Ажил хийгдсэн үед шийдэгдэнэ; хариулт нь юу хийснийг болон дараагийн ticket-үүдэд хэрэгтэй баримтуудыг (credential хаана хадгалагдсан, шинэ URL, мөрийн тоо) тэмдэглэнэ.

## Fog of war

Map _зориуд_ дутуу: хараахан харж чадахгүй зүйлээ бүү зур. Амьд ticket-үүдийн цаана **fog of war** (дайны манан) оршино: удахгүй ирэх нь мэдэгдэж байгаа ч нээлттэй асуултаас хамаардаг тул одоохондоо тодорхойлж чадахгүй шийдвэр, судалгааны бүдэг дүр зураг. Ticket шийдэх нь түүний урдах мананг арилгаж, одоо тодорхойлж болох болсон зүйлийг нэг нэгээр нь шинэ ticket болгоно, очих газар хүрэх зам тодорхой болж, ticket үлдэхгүй болтол.

Map-ын **Одоохондоо тодорхойгүй** хэсэгт тэр бүдэг дүр зургийг бичнэ: сэжиглэж буй асуулт, дараа эргэж харах хэсэг. Энэ бол очих газар _руу_ чиглэсэн, хараахан нээгдээгүй frontier: энд байгаа бүх зүйл хамрах хүрээнд байгаа, зүгээр л ticket болгох хэмжээнд тодорхой болоогүй. Харагдаж буйн хэрээр товч ч, дэлгэрэнгүй ч бич; энэ нь ажил хаашаа явж байгааг уншиж буй хамтрагчдад чиглүүлэх тэмдэг болно.

**Манан уу, ticket үү?** Шалгуур нь асуултыг одоо нарийн томъёолж чадах эсэх, одоо хариулж чадах эсэх _биш_.

- **Ticket болго:** асуулт аль хэдийн тодорхой бол, хоригдсон, одоо хийх боломжгүй байсан ч.
- **Одоохондоо тодорхойгүй-д бич:** тийм нарийн томъёолж чадахгүй хэвээр бол. Мананг урьдчилан ticket хэмжээтэй хэсгүүдэд бүү хуваа: энэ нь ticket-ээс бүдүүн, frontier хүрэхэд нэг хэсэг нь хэд хэдэн ticket болж ч болно, нэг ч болохгүй ч байж болно.

**Одоохондоо тодорхойгүй** хэсэгт аль хэдийн шийдсэн зүйл (Гаргасан шийдвэрүүд), аль хэдийн амьд ticket болсон зүйл, хамрах хүрээнээс гадуурх зүйл (дараагийн хэсэг) орохгүй.

## Хамрах хүрээнээс гадуур

Манан зөвхөн очих газар _руу_ л хуримтлагдана. Очих газар хамрах хүрээг тогтоодог тул түүнээс цаашх ажил **хамрах хүрээнээс гадуур**: энэ нь манан биш, **Одоохондоо тодорхойгүй**-д хамаарахгүй. Map дээр өөрийн **Хамрах хүрээнээс гадуур** хэсэгтэй: _энэ_ ажлаас ухамсартайгаар хассан ажил. Тодорхой байдал биш, хамрах хүрээ түүнийг энд буулгана.

Хамрах хүрээнээс гадуурх ажил хэзээ ч ticket болохгүй (frontier очих газар дээр зогсоно), тиймээс зөвхөн очих газрыг дахин зурвал л буцаж ирнэ, тэгэхдээ үргэлжлэл биш, шинэ ажил болж.

Ямар нэг зүйлийг хамрах хүрээнээс хасах нь замын алхам биш, хамрах хүрээ тогтоох үйлдэл. Аль хэдийн байгаа ticket очих газраас цаана байх нь илэрвэл (map зурах үед андуурч орсон, эсвэл ямар нэг шийдвэрээр ил гарсан) **түүнийг хаа** (хаагдсан ticket frontier-ээс эргэлзээгүй гарна), тэгээд **Хамрах хүрээнээс гадуур** хэсэгт нэг мөр үлдээ: товчлол, яагаад гадуур болсон, хаагдсан ticket-ийн холбоос. Энэ нь **Гаргасан шийдвэрүүд**-д орохгүй: тэр хэсэг бодитоор туулсан замыг тэмдэглэдэг, хамрах хүрээний хил бол түүний алхам биш.

## Дуудах

Хоёр горим. Аль нь ч бай, research ticket-ээс бусад тохиолдолд **нэг session-д нэгээс олон ticket бүү шийд**.

### Map зурах

Хэрэглэгч бүдэг санаатай дуудна.

1. **Очих газрыг нэрлэ.** Skill tool-ыг хоёр удаа, `shalgalt` болон `domain-zagvar`-ын төлөө дуудаж, энэ map юу руу зам хайж байгааг тодорхойл: spec, шийдвэр, эсвэл өөрчлөлт. Очих газар хамрах хүрээг тогтоодог тул эхлээд үүнийг шийднэ.
2. **Frontier-ийг зур.** Дахин shalgalt хий, энэ удаа **өргөнөөр нь** (breadth-first): нэг сэдэв рүү гүн орохын оронд бүх орон зайг хамарч, нээлттэй шийдвэрүүд болон одоо хийж болох эхний алхмуудыг ил гарга. **Хэрэв манан огт гарч ирэхгүй бол** (очих газар хүрэх зам аль хэдийн тодорхой, бүх аялал нэг session-д багтахаар жижиг) map хэрэггүй. Зогсоод хэрэглэгчээс яаж үргэлжлүүлэхийг асуу.
3. **Map үүсгэ** (label `zam-ol:map`): Очих газар болон Тэмдэглэл бөглөгдсөн, Гаргасан шийдвэрүүд хоосон, манан **Одоохондоо тодорхойгүй**-д тоймлогдсон.
4. **Одоо тодорхойлж болох ticket-үүдийг** map-ын child issue болгон үүсгэ, тэгээд хоригийн холбоосуудыг **хоёр дахь давталтаар** холбо (issue-нууд бие биенээ заахын өмнө id-тай болсон байх ёстой). Хоорондын ишлэлүүдийг ч тэр давталтаар бодит id-тай нь бич: `#<n>` гэсэн placeholder огт хамааралгүй issue руу автоматаар холбогдоно. Холбосноор тэд frontier болон хоригдсон гэж ангилагдана; тодорхойлж чадахгүй бүх зүйл манан дотор, **Одоохондоо тодорхойгүй** хэсэгт үлдэнэ.
5. **Research subagent-уудыг ажиллуул.** Дөнгөж үүсгэсэн `research` ticket бүрт шинэ context window-той subagent ажиллуулж, Skill tool-оор `sudal`-ыг дуудан зэрэгцээгээр шийдүүл: олдворыг хаягдах `research/<name>` branch дээр хадгалж, ticket-ээс context pointer (заагч холбоос) үлдээнэ. Branch-аа push хий, гэхдээ PR бүү нээ: энэ хэзээ ч merge хийгдэхгүй.
6. Зогс: map зурах нь нэг session-ий ажил; гараар нэг ч ticket шийдэхгүй.

### Map-аар явах

Хэрэглэгч map-тай (URL эсвэл дугаар) дуудна. Ticket заах нь **заавал биш**: заагаагүй бол дараагийн шийдвэрийг хэрэглэгч биш, чи сонгоно.

1. **Map**-ыг ачаал: ticket бүрийн биеийг биш, бага нарийвчлалтай дүр зургийг.
2. Ticket сонго. Хэрэглэгч нэрлэсэн бол түүнийг ав. Үгүй бол frontier-ийн дарааллаар эхнийхийг ав. **Эзэмш**: ямар ч ажлаас өмнө өөртөө assign хий.
3. `zam-ol:<type>` label-д заасан төрлөөр нь шийд (**Ticket-ийн төрлүүд**-ийг хар). Зөвхөн биеийг биш, label-ийг унш: бие хэзээ ч төрлийг хэлдэггүй. **Шаардлагатай хэмжээгээр томруулж хар**: холбоотой эсвэл хаагдсан аль ч ticket-ийн бүтэн биеийг хэрэгтэй үед нь татаж ав; `## Тэмдэглэл` хэсэгт нэрлэсэн skill-үүдийг Skill tool-оор дууд. Эргэлзвэл Skill tool-ыг хоёр удаа, `shalgalt` болон `domain-zagvar`-ын төлөө дууд.
4. Шийдлийг тэмдэглэ: хариултыг **шийдлийн comment** болгож нийтэл, issue-г **хаа**, map-ын Гаргасан шийдвэрүүд-д **context pointer нэм**.
5. Шинээр гарч ирсэн ticket-үүдийг нэм (эхлээд үүсгэ, дараа нь холбо); хариулт тодорхойлох боломжтой болгосон мананг ticket болго, ticket болсон хэсэг бүрийг **Одоохондоо тодорхойгүй**-гээс арилга, ингэснээр зөвхөн шинэ ticket хэлбэрээрээ үлдэнэ. Хэрэв хариулт аль нэг ticket (энэ эсвэл өөр) очих газраас цаана байгааг илрүүлбэл түүнийг замд шийдэхийн оронд **хамрах хүрээнээс гадуур болго**. Шийдвэр map-ын бусад хэсгийг хүчингүй болгосон бол тэдгээр ticket-ийг шинэчил эсвэл устга.

Хэрэглэгч хоригоос гарсан ticket-үүдийг зэрэгцээгээр ажиллуулж магадгүй, тиймээс бусад session tracker-ийг зэрэг засварлаж байгаа гэж тооц.
