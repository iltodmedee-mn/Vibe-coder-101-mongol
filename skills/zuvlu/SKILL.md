# Зөвлө

Чи бүх skill-ийг санах албагүй, асуухад л болно.

Skill юу хийдгийг хэлэх, эсвэл аль нэг алхмыг алгасахыг санал болгохоосоо өмнө тэр skill-ийн SKILL.md-г унш: энд байгаа товчлол зөвхөн чиг баримжаа өгнө.

**Хэрхэн хариулах.** Хариултаа эхэнд, дараагийн алхмаа араас нь тавь; бүх skill-ийн жагсаалтыг асгах хэрэггүй. Хэлбэр нь: аль skill, яагаад тохирох, дараагийн нэг алхам (бичих команд эсвэл хариулах нэг асуулт). Хаанаас эхлэхээ мэдэхгүй байна гэвэл богино цэс өг: "санаа байна" → үндсэн урсгал, "issue овоорсон", "ямар нэг юм эвдэрсэн", "маш том, бүрхэг ажил" → орох замууд, "кодоо цэгцлэх" → кодын эрүүл мэнд.

**Урсгал** (flow) гэдэг нь skill-үүдийг дамжих зам. Ихэнх зам нэг **үндсэн урсгал**-аар явж, **орох замууд** (on-ramp) түүнд нийлдэг. Бусад нь бие даасан, эсвэл доор нь ажилладаг үгсийн сангийн давхарга.

## Үндсэн урсгал: санаа → ship

Ихэнх ажлын явдаг зам. Чамд санаа байна, түүнийгээ бүтээлгэмээр байна.

1. **`/shalga-barimt`** санааг ярилцлагаар хурцална. **Ажлын folder-т (working directory) ажиллаж байгаа** бол үргэлж эндээс эхэл: энэ нь stateful, сурсан зүйлээ `GLOSSARY.md` ба ADR-уудад хадгалдаг. (Ажлын folder байхгүй юу? Оронд нь `/shalga`-г хэрэглэ, Бие даасан хэсэгт бий. Хоёулаа ижил `/shalgalt` суурийг (primitive) ажиллуулдаг; `shalga-barimt` нь бичгийн ул мөр үлдээдэг тул ул мөр үлдээх repo байгаа үед хоёрын илүү нь.)
2. **Салаа: бүх асуултаа ярилцаад шийдэж чадах уу?** Асуултад ажилладаг хариулт хэрэгтэй бол (state, бизнес логик, нүдээр харах ёстой UI), prototype-оор тойроод ир, хоёр чиглэлд нь **`/damjuul`**-аар холбо (prototype өөрийн folder-т амьдардаг, `/damjuul` яг үүнд зориулагдсан; Үе шатны заагийг үз):
   - **`/damjuul`**-аар гаргаад, тэр файлаар шинэ session нээ,
   - **`/turshilt`**-аар хаядаг (throwaway) кодоор асуултад хариул,
   - сурсан зүйлээ **`/damjuul`**-аар буцааж авчраад, анхны санааны thread-ээс түүнийг иш тат.
3. **Салаа: энэ олон session-ий build үү?**
   - **Тийм** → **`/spec-bolgo`** (thread-ийг spec болгоно), дараа нь **`/ticket-bolgo`**-оор tracer-bullet ticket-үүд болгон хуваа; ticket бүр өөрийн **blocking edge**-ийг (аль ticket дуусахыг хүлээхээ) зарлана. Дараа нь ticket-үүдийг хоёр аргын нэгээр хий:
     - Ticket бүрт **`/heregjuul`**, **ticket хооронд `/clear` хийж context-оо цэвэрлэ**. Local tracker дээр энэ нь `.scratch/<feature>/issues/` доор ticket бүрт нэг файл, blocker-ийг нь эхэлж гараар хийнэ; жинхэнэ tracker дээр edge-үүд native blocking холбоос болох тул blocker нь дууссан ямар ч ticket-ийг авч болно. Ticket бүр бие даасан тул өмнөхийн context хаягдаж болно.
     - Бүх spec-ийг нэг удаад **`/spec-heregjuul`**. Ticket-үүдийг **task graph** (даалгаврын граф) болгон уншиж, бэлэн болсон **frontier** (одоо эхэлж болох ticket-үүд) дээр implementer subagent-уудыг зэрэг ажиллуулж, бүгдийг нэг **integration branch** (бүх ажлыг нэгтгэдэг branch) дээр буулгана. Ticket бүрийг өөрөө жолоодохоос илүү build-ийг зохицуулахыг хүсвэл үүнийг сонго.
   - **Үгүй** → **`/heregjuul`** яг энд, нэг context window дотор.

   Аль ч тохиолдолд кодыг **`/test-ehleed`**-ээр (нэг удаад нэг red-green алхам) бичиж, **`/kod-hyana`**-аар дуусгана: diff-ийг хоёр тэнхлэгээр (Standards + Spec) хянана. `/heregjuul` ticket бүрт хоёуланг нь ажиллуулна; `/spec-heregjuul`-ийн implementer бүр `/test-ehleed`-ийг жолоодож, integration branch дээр нэг `/kod-hyana` ажиллуулна. Бүтэн spec-гүйгээр тодорхой нэг үйлдлийг test-ээ эхэлж бичээд хиймээр байвал **`/test-ehleed`**-ийг дангаар нь, тогтсон цэгээс хойших branch эсвэл PR-ийг хянах бүрт **`/kod-hyana`**-г дангаар нь хэрэглэ.

   Ажил pull request болж гарахад **`/pr-bich`** тайлбарыг нь хэлбэржүүлнэ: өөрчлөлтийг харуулах хамгийн жижиг дүрслэл, ажиллаж байгаагийн өмнө/дараах нотолгоо, буцааж болох эсэхийн дүгнэлт (two-way эсвэл one-way door). Model-invoked тул agent PR бичих бүртээ өөрөө дууддаг.

4. **`/ergen-har`** давталтыг хаана. Build-ийн дараа, ялангуяа замаасаа гарсан build-ийн дараа session-ийг эргэж харж, кодыг биш agent-ийн **орчныг** өөрчлөхийг санал болгоно: чиглүүлэх заагч, автомат шалгалт, `/kod-hyana`-гийн мөрддөг coding standard, удирдах файл, хэрэгсэл. Механик алдаа тогтмол (deterministic) шалгалт болно; шүүлтийн асуудал coding standard болно. Дараагийн build илүү сайн орчноос эхэлнэ.

### Context-ийн цэвэр байдал

1–3-р алхмыг **нэг тасралтгүй context window** дотор хий (`/ticket-bolgo`-гийн дараа хүртэл compact, clear хийхгүй), ингэснээр ярилцлага, spec, ticket бүгд нэг бодол дээр тулгуурлана. Дараа нь `/heregjuul` бүр ticket-ээсээ ажиллаж, шинээр эхэлнэ. `/ergen-har`-ыг эргэж харах session дотроо, clear хийхээсээ өмнө ажиллуул; clear хийсний дараа бол тэр session-ий log-ийг зааж өг.

Үүний хязгаар нь **smart zone** (model хурц сэтгэсээр байдаг context-ийн хэсэг): хамгийн сүүлийн үеийн model дээр ~150k token орчим. `/ticket-bolgo`-д хүрэхээс өмнө session үүнд ойртвол муудсан чигээр нь бүү тулга; хамгийн ойрын үе шатны зааг дээр `/compact` хийгээд үргэлжлүүл (Үе шатны заагийг үз).

## Орох замууд

Ажил үүсгэдэг, дараа нь үндсэн урсгалд нийлдэг эхлэлийн нөхцөл.

- **Bug, хүсэлт овоорч байна** → **`/angil`**. Issue-уудыг ангиллын (triage) үүргүүдээр дамжуулж, agent-д бэлэн issue гаргана, дараа нь **`/heregjuul`** тэднийг авна.

  Ангилал зөвхөн **чиний өөрөө үүсгээгүй** issue-д: bug report, ирж буй feature хүсэлт, түүхийгээрээ ирсэн бүх зүйл. `/ticket-bolgo`-гийн гаргасан ticket-үүд аль хэдийн agent-д бэлэн тул **тэднийг ангилах хэрэггүй**.

- **Ямар нэг юм эвдэрсэн** → **`/aldaa-zas`**. Хэцүүдэд нь: эхний харцаар олдохгүй bug, хааяа гардаг flake, хоёр сайн ажиллаж байсан төлвийн хооронд орж ирсэн regression. **Tight feedback loop** (яг *энэ* bug дээр аль хэдийн улаан болдог нэг команд) бэлэн болтол онол дэвшүүлэхгүй, дараа нь regression test-тэй засна. Засвар орсны дараа ижил session-дээ **`/ergen-har`**-ыг ажиллуулж, bug-ийг юу урьдчилан сэргийлж болох байсныг асуу; гол олдвор нь түүнийг түгжих сайн seam байхгүй гэдэг бол энэ нь **`/butets-saijruul`**-ийн ажил.

- **Маш том, бүрхэг ажил: шинэ (greenfield) төсөл эсвэл нэг session-д багтахгүй том feature** → **`/zam-ol`**, энд байгаа хамгийн их сэтгэлгээ шаарддаг урсгал. Одооноос очих газар хүрэх зам хараахан харагдахгүй үед issue tracker дээр **шийдвэрийн ticket**-үүдийн **хуваалцсан map** (газрын зураг) зурж, нэг нэгээр нь шийднэ: манан арилж зам тодрох хүртэл **бүтээгдэхүүн биш, шийдвэр** гаргана. **`/shalga-barimt`** нэг session-д багтах санааг хурцалдаг бол zam-ol нь багтахгүй санаанд зориулагдсан, илүү удаан, нягт; тиймээс яг ийм үед л хэрэглэ, хүрээ нь тодорхой feature-т үндсэн урсгал хангалттай.

  Map тодорхой болоход **энэ нь build хийдэггүй, цааш дамжуулдаг**: үндсэн урсгалд **`/spec-bolgo`**-оос нийл, тэр нь map-ын холбоотой шийдвэрүүдийг build хийж болох төлөвлөгөө болгон нэгтгэнэ, дараа нь ердийнхөөрөө `/ticket-bolgo`, `/heregjuul`. Map-аас шууд `/heregjuul` руу орвол тэр нэгтгэлийг алгасаж, холбоотой нарийн мэдээллийг хаяна; тиймээс ажил үнэхээр жижиг болж хувирсан үед л шууд `/heregjuul` руу ор.

## Кодын эрүүл мэнд

Feature ажил биш, зүгээр л арчилгаа.

- **`/butets-saijruul`**-ийг codebase-ээ agent ажиллахад тохиромжтой байлгахын тулд чөлөөт цаг гарах бүрт ажиллуул. Энэ нь **deepening opportunity** (module-ийг гүнзгийрүүлэх боломж) олж харуулна; нэгийг нь сонговол _санаа үүснэ_, түүнийгээ үндсэн урсгалд `/shalga-barimt`-аар оруул. Энэ бол нэр дэвшигчдийг олдог судалгаа; **`/kod-zagvar`** (доор) нь сонгосон нэгээ зохион бүтээх ширээ.

## Доор ажилладаг үгсийн сан

Бусад skill-үүдийн *доор* ажилладаг model-invoked хоёр лавлах; тус бүр өөрийн үгсийн сангийн цорын ганц үнэний эх сурвалж. Процесс биш **үг** асуудал болсон үед шууд дууд, эсвэл дээрх skill-үүд өөрсдөө татаж оруулна.

- **`/domain-zagvar`**: төслийн *domain*-ий хэлийг хурцална: бүрхэг нэр томъёог сорино, олон утгатай үгийг салгана (гурван ажил хийдэг "account"), буцаахад хэцүү шийдвэрийг ADR болгон тэмдэглэнэ. `/shalga-barimt` `GLOSSARY.md`-г цэвэр толь байлгахын тулд жолооддог идэвхтэй дадал.
- **`/kod-zagvar`** бол module-ийн *хэлбэрийг* зохион бүтээх deep module-ийн үгсийн сан (module, interface, depth, seam, adapter, leverage, locality): цэвэр seam дээрх жижиг interface-ийн цаана их үйлдэл. `/test-ehleed` ба `/butets-saijruul` хоёулаа энэ хэлээр ярьдаг.

## Үе шатны зааг

**Үе шат** (phase) гэдэг нь session доторх ажлын хэсэг: ярилцлага, хэрэгжүүлэлт, QA. Хоёр үе шатны **зааг** дээр чамд таван сонголт бий, тэдгээрээс сонгох нь энэ бүх зургийн хамгийн бүрхэг шийдвэр:

- **Үргэлжлүүл**: байрандаа үлд. Юу ч зарцуулахгүй, юу ч алдахгүй.
- **`/clear`**: дараагийн ажилд энд байгаа юу ч хамаагүй бол window-оо хоосол.
- **`/damjuul`** зөөж болох markdown файл бичнэ. Явцуу: зөвхөн **шинэ harness**, **шинэ folder**, **хамт ажиллагч**, эсвэл **үе шатны дундуур** хажуугийн ажил салгахад. Өгөх зүйл нь зөөвөрлөх чадвар.
- **Subagent**: нарийн хүрээтэй даалгаврыг өөрийн window руу илгээж, тайлан буцааж ав.
- **`/compact`** энэ context-ийг шахаж, шинэ session-ийг түүгээр эхлүүлнэ. **Default**, гэхдээ эхний сонголт биш: модны хамгийн доор байна.

Дараалсан модыг [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)-ээс унш: таван асуулт, салаа бүрийн учир шалтгаан, мөн анхдагч эх сурвалжийн (primary source) зардлаас болж яагаад **Үргэлжлүүл**-ийг хамгийн түрүүнд шалгах ёстой вэ. Шийдвэрийг зааг **дээр** гарга; үе шатны дундуур бол үргэлжлүүл, эсвэл үлдсэнийг subagent-уудад хуваа.

## Бие даасан

Үндсэн урсгалаас бүрэн гадна.

- **`/shalga`**: `/shalga-barimt`-тай ижил зогсолтгүй ярилцлага, гэхдээ **stateless**: local-д юу ч хадгалахгүй, `GLOSSARY.md` үүсгэхгүй. **Ажлын folder-т ажиллахгүй байгаа** үед хэрэглэ (төлөвлөгөө, дизайн, бичвэр гэх мэт доор нь repo байхгүй юуг ч хурцлах). Ажлын folder-т байгаа бол оронд нь `/shalga-barimt`-г хэрэглэ: ижил ярилцлагыг хийгээд бичгийн ул мөр үлдээдэг тул хоёрын илүү нь.
- **`/shalgalt`** бол ярилцлагын primitive өөрөө: үе (round), frontier, баримт олох нь agent-ийн ажил, шийдвэр гаргах нь чиний ажил. `/shalga` ба `/shalga-barimt` нь түүн рүү орох хоёр нэртэй хаалга; `/angil`, `/zam-ol`, `/butets-saijruul` бүгд дотроо үүнийг ажиллуулдаг. Ямар ч бүрхүүлгүй цэвэр ярилцлага хүсвэл л шууд дууд.
- **`/turshilt`** бол нэг дизайны асуултад хариулдаг жижиг, хаядаг програм: энэ state model зөв санагдаж байна уу, эсвэл энэ UI ямар байх ёстой вэ. Хаядаг гэдэг нь кодыг яаж бичих хязгаарлалт, устгана гэсэн амлалт биш: хариулт нь жинхэнэ код руу шингэж, prototype өөрөө main-аас салсан `prototype/<name>` branch дээр **анхдагч эх сурвалж** болж хадгалагдан, хэрэгжүүлэлтийн issue-ээс заагдана. Үндсэн урсгалын 2-р алхмын тойруу зам, гэхдээ дизайны асуултыг цаасан дээр шийдэхэд хэцүү үед хэзээ ч хэрэглэж болно.
- **`/sudal`**: унших ажлаа **background agent**-д даатга: тэр асуултыг **анхдагч эх сурвалжаас** шалгаад, эх сурвалжаа иш татсан Markdown файлыг repo-д үлдээнэ. Тэр уншиж байхад чи ажлаа үргэлжлүүл. Гарсан файлыг үндсэн урсгалд `/shalga-barimt`-аар оруулах материал гэж үз: судалгаа бодлыг орлохгүй, тэжээдэг.
- **`/asuulga-bolgo`** чамайг гацааж буй зүйл чиний толгойд ч, кодонд ч биш **өөр хэн нэгний** толгойд байгаа үед хэрэг болно: тэдэнд бөглөх асуулга бичнэ. Энэ нь `/shalga`-гийн эсрэг: сэдвийн талаар биш **илгээлтийн** талаар (хэнд очих, юу буцааж авах) чамаас асууж, асуултуудыг цоорхой руу онилно. Буцаж ирсэн хариулт `/shalga-barimt` эсвэл `/spec-bolgo`-д материал болно.
- **`/alham-alham`** нь зөвхөн **хүн** хийж чадах алхмуудад: дэд бүтэц бэлдэх, credential эсвэл CI secret тохируулах, танихгүй гуравдагч талын dashboard дээр дарж явах, нэг удаагийн migration эсвэл шилжилт хийх. URL бүрийг нээж, утга бүрийг авч, `.env` болон GitHub secret руу бичдэг интерактив bash script үүсгэдэг тул энэ процедурыг agent-д дахин дахин тайлбарлах шаардлагагүй болно. Model-invoked тул зөвхөн чи л давж чадах хананд тулмагц agent өөрөө дууддаг. Agent өөрөө хийж чадах зүйлээ өөрөө хийнэ; энэ нь хүн жинхэнэ оролцох ёстой газарт л.
- **`/oilgosongui`** бол ойлгогдоогүй мессежийн засвар.
