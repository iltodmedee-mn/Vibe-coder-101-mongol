# Кодын загвар

**Deep module** (гүн module) зохио: жижиг interface-ийн ард их зан төлөв, цэвэр seam дээр байрласан, тэр interface-ээрээ дамжуулан test хийгддэг. Код зохиож эсвэл бүтцийг нь өөрчилж буй хаана ч энэ хэл, зарчмуудыг хэрэглэ. Зорилго нь дуудагчдад leverage, засварлагчдад locality, бүгдэд test хийх боломж олгох.

## Нэр томъёо

Эдгээр нэр томъёог яг хэрэглэ: "component", "service", "API", "boundary"-гаар бүү соль, Монгол орчуулгаар нь ч бүү соль. Тогтвортой хэл бол гол санаа нь.

**Module**: interface ба implementation-тэй бүх зүйл. Хэмжээнээс санаатайгаар үл хамаарна: function, class, package, эсвэл хэд хэдэн давхаргыг (tier) хөндлөн огтолсон хэсэг. _Avoid_: unit, component, service.

**Interface**: module-ийг зөв хэрэглэхийн тулд дуудагчийн мэдэх ёстой бүх зүйл: type signature, мөн invariant (үргэлж үнэн байх нөхцөл), дарааллын хязгаарлалт, алдааны горим, шаардлагатай тохиргоо, гүйцэтгэлийн онцлог. _Avoid_: API, signature (хэт явцуу, зөвхөн type түвшний гадаргууг хэлдэг).

**Implementation**: module-ийн дотор байгаа зүйл, кодын бие. **Adapter**-аас ялгаатай: нэг зүйл жижиг adapter боловч том implementation-тэй (Postgres repo), эсвэл том adapter боловч жижиг implementation-тэй (in-memory fake) байж болно. Seam сэдэв болж байвал "adapter", бусад үед "implementation" гэж хэл.

**Depth** (гүн): interface дээрх leverage. Дуудагч (эсвэл test) сурах ёстой interface-ийн нэгж тутамд ажиллуулж чадах зан төлөвийн хэмжээ. Жижиг interface-ийн ард их зан төлөв байвал module **deep**, interface нь implementation-тэйгээ бараг адил нарийн бол **shallow** (гүехэн).

**Seam** _(Michael Feathers)_: тухайн газрыг засварлахгүйгээр зан төлөвийг өөрчилж болох газар; module-ийн interface оршдог *байршил*. Seam-ийг хаана тавих нь түүний ард юу байхаас тусдаа, бие даасан дизайны шийдвэр. _Avoid_: boundary (DDD-гийн bounded context-тэй давхцаж утга нь бүрхэгдэнэ).

**Adapter**: seam дээр interface-ийг хангаж буй бодит зүйл. *Үүргийг* (ямар үүрийг дүүргэх) хэлнэ, агуулгыг (дотор нь юу байгааг) биш.

**Leverage** (хөшүүрэг): depth-ээс дуудагчийн авах ашиг. Сурах interface-ийн нэгж тутамд илүү их чадвар. Нэг implementation N дуудах газар, M test дээр өгөөжөө өгнө.

**Locality** (нэг газарт төвлөрөх): depth-ээс засварлагчийн авах ашиг. Өөрчлөлт, bug, мэдлэг, шалгалт дуудагчдын дунд тархахын оронд нэг газарт төвлөрнө. Нэг засвал, хаа сайгүй засагдана.

## Deep ба shallow

**Deep module** = жижиг interface + их implementation:

```
┌─────────────────────┐
│   Жижиг interface   │  ← Цөөн method, энгийн параметр
├─────────────────────┤
│                     │
│  Deep implementation│  ← Нарийн логик дотроо нуугдсан
│                     │
└─────────────────────┘
```

**Shallow module** = том interface + бага implementation (зайлсхий):

```
┌─────────────────────────────────┐
│       Том interface             │  ← Олон method, нарийн параметр
├─────────────────────────────────┤
│  Нимгэн implementation          │  ← Зүгээр л цааш дамжуулна
└─────────────────────────────────┘
```

Interface зохиохдоо өөрөөсөө асуу:

- Method-уудын тоог цөөлж болох уу?
- Параметрүүдийг хялбарчилж болох уу?
- Илүү их нарийн төвөгтэй байдлыг дотор нь нууж болох уу?

## Зарчмууд

- **Depth бол implementation-ий биш, interface-ийн шинж чанар.** Deep module дотроо жижиг, mock хийж болох, сольж болох хэсгүүдээс бүтэж болно; тэд зүгээр л interface-ийн нэг хэсэг биш. Module interface дээрээ **гадаад seam**-тэй байхаас гадна **дотоод seam**-тэй (implementation-дээ хувийн, өөрийн test-үүддээ хэрэглэдэг) байж болно.
- **Deletion test** (устгах туршилт). Module-ийг устгалаа гэж төсөөл. Нарийн төвөгтэй байдал алга болбол тэр зүгээр л дамжуулагч байсан. N дуудагч дээр дахин гарч ирвэл тэр өөрийн үүргээ гүйцэтгэж байсан.
- **Interface бол test-ийн гадаргуу.** Дуудагч ба test нэг seam-ийг давна. Interface-ийг *давж* test хийх хүсэл төрвөл module буруу хэлбэртэй байх магадлалтай.
- **Нэг adapter бол таамаг seam. Хоёр adapter бол жинхэнэ seam.** Цаана нь ямар нэг зүйл үнэхээр өөрчлөгддөггүй бол seam бүү нэм.

## Test хийхэд зориулсан дизайн

Сайн interface test хийхийг аяндаа хялбар болгоно:

1. **Хамаарлаа дотроо үүсгэх биш, гаднаас хүлээж ав.**

   ```typescript
   // Test хийхэд хялбар
   function processOrder(order, paymentGateway) {}

   // Test хийхэд хэцүү
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **Хажуугийн нөлөө (side effect) үүсгэх биш, үр дүн буцаа.**

   ```typescript
   // Test хийхэд хялбар
   function calculateDiscount(cart): Discount {}

   // Test хийхэд хэцүү
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **Жижиг гадаргуу.** Цөөн method = цөөн test. Цөөн параметр = test-ийн бэлтгэл хялбар.

## Хамаарал

- **Module** яг нэг **Interface**-тэй (дуудагч ба test-д харагдах гадаргуу).
- **Depth** бол **Module**-ийн шинж чанар, түүний **Interface**-тэй харьцуулж хэмжинэ.
- **Seam** бол **Module**-ийн **Interface** оршдог газар.
- **Adapter** **Seam** дээр сууж, **Interface**-ийг хангана.
- **Depth** дуудагчдад **Leverage**, засварлагчдад **Locality** өгнө.

## Татгалзсан ойлголтууд

- **Depth-ийг implementation-ий мөрийн тоог interface-ийн мөрийн тоонд харьцуулсан харьцаа гэж үзэх** (Ousterhout): implementation-ийг дэмий хөөргөхийг шагнадаг. Бид оронд нь depth-ийг leverage гэж үздэг.
- **"Interface"-ийг TypeScript-ийн `interface` түлхүүр үг эсвэл class-ын public method-ууд гэж үзэх**: хэт явцуу; энд interface гэдэг нь дуудагчийн мэдэх ёстой бүх баримтыг багтаана.
- **"Boundary"**: DDD-гийн bounded context-тэй давхцана. **seam** эсвэл **interface** гэж хэл.
