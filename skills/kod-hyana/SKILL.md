`HEAD` ба хэрэглэгчийн өгсөн тогтсон цэгийн (fixed point) хоорондох diff-ийг хоёр тэнхлэгээр хянана:

- **Standards**: код энэ repo-гийн бичигдсэн кодын стандартад нийцэж байна уу?
- **Spec**: код анхны issue / spec-ийг үнэн зөв хэрэгжүүлсэн үү?

Хоёр тэнхлэг бие биенийхээ context-ийг бохирдуулахгүйн тулд **зэрэгцээ sub-agent** болж ажиллана, дараа нь энэ skill тэдний олсныг нэгтгэнэ. Sub-agent бүрийг шинэ, цэвэр context window-оор эхлүүл.

Issue tracker чамд өгөгдсөн байх ёстой. Өгөгдөөгүй бол хэрэглэгчид `/tohiruul`-ыг ажиллуулахыг хэл.

## Явц

### 1. Тогтсон цэгээ тогтоо

Хэрэглэгчийн хэлсэн зүйл л тогтсон цэг болно (commit SHA, branch-ийн нэр, tag, `main`, `HEAD~5` гэх мэт). Хэлээгүй бол асуу.

Diff-ийн командыг нэг удаа тогтоож ав: `git diff <fixed-point>...HEAD` (гурван цэгтэй, тэгвэл merge-base-тэй харьцуулна). Мөн commit-уудын жагсаалтыг `git log <fixed-point>..HEAD --oneline`-аар тэмдэглэж ав.

Цааш явахаас өмнө тогтсон цэг олдож байгааг (`git rev-parse <fixed-point>`), diff хоосон биш гэдгийг шалга. Буруу ref эсвэл хоосон diff хоёр зэрэгцээ sub-agent дотор биш, яг энд унах ёстой.

### 2. Spec-ийн эх сурвалжийг ол

Анхны spec-ийг дараах дарааллаар хай:

1. Commit message доторх issue-ийн ишлэл (`#123`, `Closes #45`, GitLab `!67` гэх мэт); tracker-ийн баримтад заасан аргаар татаж ав.
2. Хэрэглэгчийн аргументаар өгсөн зам.
3. `docs/`, `specs/`, `.scratch/` дотор branch-ийн нэр эсвэл feature-тэй таарах spec файл.
4. Юу ч олдохгүй бол spec хаана байгааг хэрэглэгчээс асуу. Байхгүй гэвэл **Spec** sub-agent-ыг алгасаж, "spec байхгүй" гэж тайлагнана.

### 3. Стандартын эх сурвалжуудыг ол

Код хэрхэн бичихийг заасан бүх файлыг repo-оос хай. `CODING_STANDARDS.md` эсвэл `CONTRIBUTING.md` байвал заавал жагсаалтад орно.

Repo-д юу бичигдсэнээс гадна Standards тэнхлэг үргэлж доорх **smell-ийн суурь жагсаалтыг** авч явна: Fowler-ийн code smell-үүдээс (_Refactoring_, 3-р бүлэг) сонгосон тогтмол багц, repo юу ч бичээгүй байсан ч хэрэгжинэ. Хоёр дүрэм үүнийг хязгаарлана:

- **Repo давамгайлна.** Repo-гийн бичигдсэн стандарт үргэлж ялна; суурь жагсаалтын тэмдэглэх зүйлийг repo зөвшөөрсөн бол тэр smell-ийг бүү гарга.
- **Үргэлж дүгнэлтийн асуудал.** Smell бүр "Feature Envy байж магадгүй" гэх мэт шошготой таамаг, хэзээ ч хатуу зөрчил биш. Энд байгаа бусад стандартын адил, хэрэгсэл (tooling) аль хэдийн шалгадаг зүйлийг алгас.

Smell бүр *юу вэ* → *яаж засах* гэж уншигдана; diff-тэй тулгаж үз:

- **Mysterious Name**: юу хийдэг, юу агуулдгаа нэрээрээ илэрхийлдэггүй function, хувьсагч, type. → нэрийг нь соль; үнэн нэр олдохгүй бол дизайн нь бүрхэг байна.
- **Duplicated Code**: ижил логикийн хэлбэр өөрчлөлтийн нэгээс олон hunk эсвэл файлд гарна. → нийтлэг хэлбэрийг салгаж аваад, хоёр газраас нь дууд.
- **Feature Envy**: өөрийнхөөсөө илүү өөр объектын өгөгдөл рүү гар сунгадаг method. → method-ыг атаархаж буй өгөгдөл рүү нь зөө.
- **Data Clumps**: цөөн хэдэн талбар эсвэл параметр байнга хамт явна (төрөх гэж буй type). → нэг type болгож багцлаад, түүнийг дамжуул.
- **Primitive Obsession**: өөрийн type авах ёстой domain-ий ойлголтыг primitive эсвэл string орлож байна. → тэр ойлголтод өөрийн жижиг type өг.
- **Repeated Switches**: нэг type дээрх ижил `switch`/`if` шат өөрчлөлтийн дотор давтагдана. → polymorphism-оор, эсвэл хоёр газар хуваалцах нэг map-аар соль.
- **Shotgun Surgery**: нэг логик өөрчлөлт diff доторх олон файлд тархсан засвар шаардана. → хамт өөрчлөгддөг зүйлсийг нэг module-д цуглуул.
- **Divergent Change**: нэг файл эсвэл module хоорондоо хамааралгүй хэд хэдэн шалтгаанаар засагдана. → module бүр нэг л шалтгаанаар өөрчлөгдөхөөр хуваа.
- **Speculative Generality**: spec-д байхгүй хэрэгцээнд зориулж нэмсэн abstraction, параметр, hook. → устга; бодит хэрэгцээ гарч иртэл буцааж inline хий.
- **Message Chains**: дуудагч хамаарах ёсгүй урт `a.b().c().d()` гинж. → тэр замыг эхний объектын нэг method-ын ард нуу.
- **Middle Man**: ихэвчлэн зөвхөн цааш дамжуулдаг class эсвэл function. → тасалж хаяад, жинхэнэ зорилт руу шууд дууд.
- **Refused Bequest**: өвлөсөн зүйлийнхээ ихэнхийг үл тоодог эсвэл дарж бичдэг subclass эсвэл implementer. → inheritance-ийг хаяад composition хэрэглэ.

Standards тэнхлэг мөн **аюулгүй байдлын суурь жагсаалтыг** авч явна. Smell-ээс ялгаатай нь эдгээр нь бодит эвдрэлийн хувилбарыг (ямар оролт → ямар муу үр дүн) нэрлэж чадвал хатуу зөрчил болно:

- **Код дотор бичсэн нууц**: API key, нууц үг, token эх кодонд шууд бичигдсэн. → environment variable (`.env`) руу зөөж, `.env`-ийг git-ээс гадуур байлга.
- **Injection**: хэрэглэгчийн оролтыг SQL query-д шууд залгасан, эсвэл түүхий HTML болгож харуулсан. → parameterized query хэрэглэ, оролтыг escape хий.
- **Эрхийн шалгалт дутуу**: хэн болохыг шалгалгүйгээр өгөгдөл уншдаг эсвэл өөрчилдөг endpoint. → нэвтрэлт, эрхийн шалгалт нэм.
- **Log-д гарсан нууц**: token, нууц үг, хувийн мэдээллийг log руу бичиж байна. → log-оос хас.

### 4. Хоёр sub-agent-ыг зэрэгцээ ажиллуул

Хоёр sub-agent-ыг нэг дор, foreground-д дуудаж, буцаасан тайланг нь нэгтгэ.

Хоёуланд нь **шуугианы шүүлтүүрийг** өг:

- Файл, мөрийг нь зааж, бодит эвдрэлийг (ямар оролт, ямар төлөв → ямар муу үр дүн) нэрлэж чадах зүйлийг л мэдээл. Чадахгүй бол хас.
- Тэмдэглэхээсээ өмнө тэр хэсгийг дууддаг газар, import, test-ийг унш; асуудал тэнд аль хэдийн шийдэгдсэн байж магадгүй.
- Ижил төстэй олдворуудыг нэгтгэ ("5 function алдаа барьдаггүй", 5 тусдаа мөр биш).
- Олдворгүй хяналт бол зөв хяналт. Ажилласан мэт харагдах гэж олдвор бүү зохио.

**Standards sub-agent-ийн prompt**-д дараахыг оруул:

- Diff-ийн бүтэн команд ба commit-уудын жагсаалт.
- 3-р алхамд олсон стандартын эх файлуудын жагсаалт, **дээр нь 3-р алхмын smell-ийн ба аюулгүй байдлын суурь жагсаалтыг** бүтнээр нь хуулж оруул (sub-agent өөр замаар түүнийг харахгүй).
- Шуугианы шүүлтүүр.
- Даалгавар: "Файл/hunk бүрээр (a) diff бичигдсэн стандартыг зөрчсөн газар бүрийг: стандартаа (файл + дүрэм) иш татаж; (b) олж харсан суурь smell-ийг: нэрийг нь хэлж, hunk-ийг иш татаж; (c) аюулгүй байдлын суурь жагсаалтын зөрчлийг: мөр ба эвдрэлийн хувилбартай нь мэдээл. Хатуу зөрчлийг дүгнэлтийн асуудлаас ялга: бичигдсэн стандартын болон аюулгүй байдлын зөрчил хатуу байж болно, харин суурь smell үргэлж дүгнэлтийн асуудал, repo-гийн бичигдсэн стандарт суурь smell-ийг давамгайлна. Хэрэгсэл шалгадаг зүйлийг алгас. 400 үгээс бага."

**Spec sub-agent-ийн prompt**-д дараахыг оруул:

- Diff-ийн команд ба commit-уудын жагсаалт.
- Spec-ийн зам эсвэл татаж авсан агуулга.
- Шуугианы шүүлтүүр.
- Даалгавар: "Мэдээл: (a) spec-д хүссэн боловч дутуу эсвэл огт хийгдээгүй шаардлага; (b) diff дотор хүсээгүй байхад нэмэгдсэн зан төлөв (scope creep); (c) хэрэгжсэн мэт харагдах боловч буруу хийгдсэн бололтой шаардлага. Олдвор бүрд spec-ийн мөрийг иш тат. 400 үгээс бага."

Spec байхгүй бол Spec sub-agent-ыг алгасаж, эцсийн тайланд үүнийгээ тэмдэглэ.

### 5. Нэгтгэ

Хоёр тайланг `## Standards` ба `## Spec` гарчгийн дор, байгаагаар нь эсвэл бага зэрэг цэвэрлэж харуул. Олдворуудыг бүү нийлүүл, дахин бүү эрэмбэл, учир нь хоёр тэнхлэгийг санаатайгаар тусгаарласан (_Яагаад хоёр тэнхлэг_-ийг үз).

Олдвор бүрийг хэрэглэгч ойлгохоор энгийн үгээр бич: хаана, юу буруу, яаж засах. Хүнийг биш, кодыг шүүмжил.

Эцэст нь нэг мөр хураангуй бич: тэнхлэг бүрийн нийт олдворын тоо, мөн _тэнхлэг бүрийн доторх_ хамгийн ноцтой асуудал (байвал). Хоёр тэнхлэгийн дундаас нэг ялагч бүү сонго: тусгаарлалт яг ийм дахин эрэмбэлэлтээс сэргийлэхийн тулд байгаа.

## Яагаад хоёр тэнхлэг

Өөрчлөлт нэг тэнхлэгийг давж, нөгөөд унаж болно:

- Бүх стандартыг мөрдсөн ч буруу зүйл хэрэгжүүлсэн код → **Standards давна, Spec унана.**
- Issue-д хүссэнийг яг хийсэн ч төслийн дүрмийг зөрчсөн код → **Spec давна, Standards унана.**

Тусад нь тайлагнавал нэг тэнхлэг нөгөөгөө халхлахгүй.
